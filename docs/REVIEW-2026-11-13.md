# Architecture and design review, 2026-11-13 (at 6b91684)

Scope: the design as a whole, read from every crate, the Nix integration and the documents;
not a line-by-line bug hunt. The project map is [`ARCHITECTURE.md`](ARCHITECTURE.md). IDs use
the prefix **A** so they do not collide with [`REVIEW-2026-11-11.md`](REVIEW-2026-11-11.md).

Evidence is code reading throughout; nothing here was reproduced with a test. Fixes made the
same day are listed under [Status](#status-2026-11-13); the findings table keeps the text as
found.

## Verdict

**The core design has no fundamental flaw.** Content-addressed identity, material-first public
keys with host-side proof of possession, the closed-world policy vector, linking only through
a shared scheme, and a pure, property-tested rule engine (`core::reconcile`) are sound and
unusually well pinned by tests.

The risks are around the core, not in it:

1. The guarantee is stated more strongly than it holds (A1), and one default weakens it (A2).
2. About 40% of the code serves features beside "pin and verify" (profiles, migration
   planning, attestation), built before the lock format and the consumer contract are settled
   (A4, A5, A6, A8).
3. The lock repeats token facts per realisation, which hurts the review-the-diff workflow the
   design relies on (A3).

## A3: the observation table

A single `[tokens.<name>]` table would assume that every realisation on a token saw the same
module, firmware and mechanism list. They need not: realisations are recorded at different
times, from different hosts, and through different modules (direct and p11-kit).

So the table makes no such claim. It holds each **distinct observation** once, keyed by a hash
of its own content, and a realisation names the one it was recorded with:

```toml
[observations."sha256-Qm…"]        # module, token info, provider, mechanism list
…

[realisations.signing-soft.softhsm]
observation = "sha256-Qm…"         # was: ~30 lines of observed.mechanisms and provenance.*
```

- **It only deduplicates.** A realisation still says exactly what it was recorded with. Two
  realisations recorded with different module builds point at two entries.
- **`uri` and `session` stay on the realisation;** they are per object and per run.
- **A module update shows as one new entry** and one changed line per realisation re-recorded,
  not thirty lines in each.
- **`gc` drops entries nothing references.**
- **What it does not answer:** which observation is the token's *current* one. `gate` and
  `migrate` take the first they find today. With the table they can use the token's
  observation when all its realisations agree, and otherwise say so and name `realise` as the
  way to refresh. A recorded time would answer it too, but would change the lock on every
  write.

Not decided: A7 (open by choice), and for A1 the verified-at time in CONTRACT.md.

## Threat model (draft, inferred from the code)

Nothing in the repository states this; it is what the mechanisms add up to.

| Defended | By |
|---|---|
| The wrong object under the right label or `CKA_ID` (mistake, restore, re-import, another device) | Recomputed CA-IDs against the lock |
| A private key swapped beside a public object or certificate that was left in place | Proof of possession, verified on the host |
| A module that reports a public key it does not hold | Material first; `CKA_PUBLIC_KEY_INFO` only cross-checked |
| Policy or type drift since review | Spec digest, closed-world policy vector, immutables |
| Silent weakening of how identity is established | Mode, binding, scheme and attestation downgrade rules |
| A token reaching builds that did not ask for it | The pre-build hook |
| A token echoing lock values ("pass the hash") | Every ID is a SHA-256 the host computes from what it reads; the token never sees or returns a lock value |
| A replayed proof of possession (private keys) | A fresh challenge per proof, verified on the host (§ Replay below) |

| Not defended | Why |
|---|---|
| Whoever can change `keys.lock` (or `keys.toml`) | The lock is the trust root; its integrity is the repository's |
| A swap between `check` and the use that follows | The consumer opens the URI itself |
| A build served from cache | The token is not contacted |
| A derivation that names the token's feature | Features are self-declared; the gate is `allowed-users` |
| A malicious module or token after the check | It can pass the proof, then sign with anything |
| Copies of the key elsewhere | Unobservable |
| A secret key's commitment replayed by anything that saw it once | Deterministic output of a fixed input; the host holds no key to check a fresh one (§ Replay below) |
| Public material, and private keys without a proof (`token-asserted`, `publicOnly`), returned by whoever has the bytes | Public data proves no secret |
| A challenge relayed to the genuine token elsewhere | A proof shows access to the key, not where the key is |

### Replay

**The question.** Can a malicious module or token, or anything on the PKCS#11 path (a p11-kit
forwarder, a trace or log), pass a check without holding the key? It could answer with values it
saw in an earlier run, or values computed from the lock file.

**What the lock gives away.** Echoing the lock's values does not work. Every ID is a SHA-256 the
host computes itself from what the token returns, so a forger needs the bytes behind the hash,
never the hash. The question that remains is whether those bytes can be replayed, which depends
on the scheme.

**Replay-safe where possible.** The rule is: wherever a fresh challenge can be verified, cakeys
uses one; where it cannot, the scheme is a fingerprint and is named as one.

| What's checked | Replayable? | Why |
|---|---|---|
| **Private keys** (`pop-sign`, `pop-ecdh`, `pop-decrypt`) | **No** | Each proof is over a fresh random 32-byte challenge (OS RNG, domain-separated) and is checked on the host against the locked public key. Only the private key can answer. `pop-ecdh`'s extractable path compares a secret derived against a fresh ephemeral host key. |
| **Private keys with `binding = "token-asserted"` or `publicOnly`** (Ed448 is forced to `token-asserted`: no host verifier yet) | **Yes** | Only the public key is checked, and it is public. |
| **Public keys, certificates, data objects** (`rfc7093m4`, `certhash`, `valuehash`) | **Yes, by design** | Anyone holding the bytes can return them. This checks content integrity, not possession of a secret. |
| **Secret keys** (AES, HMAC: `cmac`, `kcv-ecb`, `kcv-ecb-dec`, `kw`, `commitment`) | **Yes** | The token MACs or encrypts a fixed input derived from the label, and the lock stores the SHA-256 of the output. The lock alone does not let anyone forge the output. But the output never changes, so anything that saw it once can return it without the key: the token, the module, a forwarder, a trace, or the realising run itself. A token that held the key at `realise` can drop it and keep passing. |
| **YubiKey attestation** (`piv-attestation`) | The certificate can be replayed | Yubico's certificate carries no verifier nonce (DESIGN §3.7). It names the public key, and the private-key proof still runs, so a replay alone does not pass. |
| **TPM attestation** (`tpm-certify`) | **No** | `TPM2_Certify` signs a fresh nonce. Until the Attestation Key chains to an EK certificate it proves "the same TPM as at first use", not "a genuine TPM" (A8). |

**Why secret keys cannot be made replay-safe in general.** A fresh challenge helps only if the
verifier can check the answer. For a private key the host checks it against the public key. A
symmetric key has no public counterpart, and cakeys holds no secret, by design: the lock is
public data, and checks run in sandboxes. A verifier that holds nothing secret cannot tell a party
that knows the key from one that has recorded every answer the verifier could expect. Every
answer the verifier can check, it could also have computed, so the forger can too.

What remains for secret keys:

- **TPM attestation:** `tpm-certify` proves the secret key is loaded in that TPM, bound to a
  nonce. It is TPM-only, and its anchor is limited as above.
- **A challenge bank** (not implemented): `realise` records the answers to N random
  challenges, and each check asks one of them. This defends only against a party that did not
  see `realise`, and only probabilistically, since the challenges sit in the public lock. It does
  nothing against a token that was malicious at `realise`.
- **Saying so (done):** every realisation carries an `assurance`, in the `realise`/`resolve`
  JSON and in the Nix view (`keys.<object> { ... }.assurance`): `proof`, `fingerprint` or
  `public`, per the table above (`cakeys_core::plan::assurance`). It is derived from the class,
  the recorded binding and the attestation kind, so the lock format is unchanged.
- **Hiding the challenge does not help.** Keeping the fixed input secret, for instance as
  challenges stored only on the token, changes nothing. Nobody without the key can compute an
  answer for any input, public or not. And the parties that can replay, the token and the
  modules on its path, see wherever the challenge is stored. Only a secret the *verifier*
  holds, and the token has not yet seen, makes an answer fresh (NEXT.md §2c).

## Unnecessary complexity, in order of payoff

1. Add the lock's observation table and drop per-realisation provenance (A3): smaller locks,
   simpler `gate` and `migrate` lookups, readable diffs.

Deferred by the decisions above: the unimplemented modes and `identity.allow` (A6, pending
implementation), the unused `Provider::mechanisms` and `Provider::migration` hooks (A4, kept
for real HSM providers), `autoCreate` in `check` (A7, open), and where the migrate code lives
(A5, before migration is complete).

## What is sound and should be kept

- The split of `cakeys-core` (pure) from `cakeys-pkcs11` (token): every lock rule is testable
  without an HSM, and is tested with proptest.
- Exit codes as the error model, and one exit-code order inside `compare`.
- The compared / observed / provenance split of the lock.
- The provider fix-up rule ("return what a compliant module would"), which keeps identities
  portable.
- Integration tests through the real CLI against real modules, with independent oracles, and
  the cross-token suite.
- Native dependencies behind cargo features; `checks.minimal` proves the split.
