# Architecture review, 2026-11-15: the verbs, the Nix library, and the config and profile data

Reviewed at `95258f9` (origin/main). Scope: what cakeys adds on top of PKCS#11, the TPM and
cryptoki. That is the verbs (`crates/pkcs11/src/ops.rs`, `crates/cli`), the Nix integration
(`nix/lib.nix`, `nix/module.nix`, `nix/sandbox-hook.sh`), and the data: keys.toml, keys.lock,
the capability profiles and the `Provider` trait. camigrate and caprobe were read only where
they shape that data.

Role: advisory. No source file is changed by this review. Two throwaway tests reproduced
findings P1 and C1 and were removed again; the Nix library was probed by evaluation.

Each finding is tagged **[run]** (reproduced here) or **[read]** (from the code, not run).

## Summary

- **The resource model is sound.** An object is material, a spec is an assertion about it, a
  realisation is the pair (spec, token), and the lock rules are pure functions in `cakeys-core`.
  Nothing below asks to change that.
- **The verbs mix concerns in one place that matters:** `check` is implemented as
  `realise` without the lock write, so the verb documented as a GET creates keys, provisions
  the TPM Attestation Key and demands generation mechanisms. `verify`, `check`, `realise` and
  `create` are one function with three booleans; the names do not say which booleans.
- **The Nix library re-implements Rust rules and validates nothing,** and it hands out the
  lock's URI at evaluation time, which the design says a program must never use unverified.
- **keys.toml is not boxed in, but should close three holes before its keys freeze:** no
  grammar for names, two specs may both create one object on one token, and tool-specific
  settings sit in the core schema.
- **The capability profiles are chasing something that cannot be completely described,** and
  today a gap in the description is fatal: a module version bump refuses every verb that
  opens the token, for the three families with two profiles (aws-cloudhsm, tpm2-pkcs11,
  kmsp11). The fix is to change what is described, from "what the module does" to "which of
  cakeys' own operations work", and to make a missing answer mean "try it".

Decided with the author on 2026-11-15, and written into the sections below: `check` becomes
a pure read and keys are created only by `cakeys create`; `autoCreate` goes; `realise` is the
lock verb, re-records as a lock file does and takes no `--accept-drift`; it keeps
provisioning the Attestation Key for now; exit codes and keys.toml keys are renamed in place.

## 1. The verbs

The analogy holds for the resource: a realisation is addressed, read, created with
If-None-Match and deleted with If-Match. It breaks on which store a verb writes. There are two
stores, the token and the lock, plus the TPM's persistent handles:

| Verb | Creates on the token | Provisions the AK | Writes the lock | Addressed by |
|---|---|---|---|---|
| `resolve` | no | no | no | `<spec> --token` |
| `verify` | no | no | no | `<spec> --token` |
| `check` | **yes, with `autoCreate`** | **yes** | no | `<object>[.id.<scheme>] [--spec] [--token]` |
| `realise --no-update-lock` | yes, with `autoCreate` | yes | no | `<spec> --token` |
| `realise` | yes, with `autoCreate` | yes | yes | `<spec> --token` |
| `create` | yes | yes | yes | `[<spec>] [--token]` |
| `delete` | deletes | no | yes | `<spec> --token` |

### V1. `check` is a PUT that is documented as a GET [read]

`ops::check_open` calls `realise(…, LockWrite::Compare, …)` (`ops.rs:772`), and `realise_as`
always resolves with `provision = true` (`ops.rs:394`). So `check`:

- creates the key when `autoCreate` is set and the locator is empty, then exits 10. A key now
  exists that no lock records, made by whatever could run a build or start a unit;
- provisions a missing Attestation Key at its persistent handle (`esys.rs:96` is the only
  guard, and `provision` is true). DESIGN §3.7 says "`resolve`, `verify` and `check` never
  change the TPM"; `tpm2.rs` tests that for `verify` only;
- runs `check_capabilities`, whose `needs` adds the generation mechanism whenever
  `autoCreate` is set (`ops.rs:115`), whether or not the object exists. A key created through
  the vendor module and checked through p11-kit, which drops Edwards generation, is refused
  (15) although it is there and verifiable. That is the "one token through two modules" item
  of OPEN.md, hit from the read side.

CAKEYS.md says "`resolve`, `verify` and `check` are GETs and never write" and ARCHITECTURE.md
says "`check`: read, or write with `autoCreate`". Both cannot be right.

**Decided (2026-11-15):** `check` becomes `verify` addressed by object: resolve, compare, the
scheme pin, the output formats. No creation, no provisioning, a read-only session always.
Creation is out of band only (`cakeys create`). The fixed-output style of first use stays: a
key that exists and is not pinned still fails with `got:`; only a key that does not exist
fails "not found; run `cakeys create`". This settles OPEN.md's "`autoCreate` on `check`".

### V2. `realise` is three operations [read]

It creates when absent (a token write), pins on first use (a lock write, trust on first use),
and re-accepts drift: with the write on, `compare` skips `spec_unchanged` and
`object_unchanged` (`reconcile.rs:187-193`), so a changed locator, spec digest or undeclared
policy attribute is re-recorded with a line on stderr. An operator who runs `realise` to make
sure a key exists has also accepted whatever the token's policy became.

**Decided (2026-11-15):** `realise` is the lock verb, with lock-file semantics: it records
what is there now, also when nothing about the key changed (a module path or hash, a version,
provenance). No `--accept-drift`. What a writing `realise` re-records falls into three kinds,
and none needs a flag:

| What changed | On `realise` | Why no gate |
|---|---|---|
| Module, versions, provider, mechanisms, token info | re-recorded, a note or warning | the lock-file behaviour wanted |
| keys.toml (locator, object, `publicOnly`, spec digest) | re-recorded, a note | the author's own change; the keys.toml diff is its review |
| An undeclared policy attribute on the token | re-recorded, a warning | the gate exists: declare the attribute, and a mismatch is a conflict (13), never re-recorded |

So the rule to document in CONFIG.md is: **declare what must not drift; everything else is
observed.** IDs, downgrades, immutables, attestations and types stay refused even when writing.

With `check` no longer creating, `autoCreate` would only affect `realise`, which `create`
already covers: **drop `autoCreate`.** `realise` then never creates, and the set is orthogonal:

- token: `create` (PUT If-None-Match), `delete` (DELETE If-Match);
- lock: `realise` (record what is there), `gc`;
- read: `resolve` (no lock), `check` (If-Match).

**The Attestation Key (decided 2026-11-15: `realise` keeps provisioning it, to revisit).** It
is the one device write the lock verb still makes, and `create` makes it through `realise`.
The AK is not a precondition of the key it certifies: the key lives under the token's own
primary and is found and identified without one; the AK only signs the certify of a spec that
opted into attestation. It is a primary (`TPM2_CreatePrimary` in the owner hierarchy from a
fixed template, `esys.rs:103`), so the TPM derives the same key from its owner seed whoever
asks and whenever, until the TPM is cleared; `TPM2_EvictControl` only keeps a copy at a
handle [read]. For the revisit, two ways to take the write out of `realise`: a set-up step of
its own (not `create`: an imported key is attested too), or persisting nothing, each
attestation creating the primary, certifying and flushing it, which needs owner authorization
on every run where a persisted key needs it once.

### V3. Exit 10 means two opposite things [read]

A mismatch against a pinned ID and a first use with nothing pinned both exit 10
(`reconcile.rs:376`, `:386`). CAKEYS.md asks callers to keep them apart ("a security event"
against "the state before `realise`"), and gives them only stderr to do it with. A matching
object whose realisation is not recorded is 14, so "the lock lacks it" already has two codes.
`reconcile`'s own rustdoc says first use is `PreconditionFailed`; the code returns
`HashMismatch`.

**Recommendation:** first use gets its own code before the codes freeze. HTTP has it: 428
Precondition Required.

### V4. Two address grammars, and `verify` duplicates `check` [read]

`verify` and `check` differ by how the pair is named and by nothing else once V1 is fixed.
An unknown token is 17 but an unknown spec is 11. `resolve` and `realise` print JSON,
`verify` and `check` a URI.

**Recommendation:** one grammar for every verb, object first
(`<object>[.id.<scheme>] [--spec] [--token]`), since the interface names objects. Drop
`verify` or make it an alias.

### V5. Object types are validated per target [read]

`certificateType`, the key type and curve pairing and `publicOnly` rules live in `plan_mode`,
which runs per (spec, token). An object no spec uses is never validated, and each object is
re-validated once per pair.

## 2. The Nix integration

### N1. The view exposes the unverified URI [run]

`keys.<obj> { }.uri` is `real.observed.uri` (`lib.nix:147`). LOCK.md classes `observed` as
never deciding a verdict and safe to remove; CAKEYS.md says a program names an object, never
a URI, and that the URI is what `check` hands back. The library hands it back at evaluation,
with no check. A consumer that interpolates `.uri` builds and never contacts the token.

**Recommendation:** remove `uri` from the view (or name it `unverifiedUri`). `module`,
`tokenInfo` and `functions` are observations too; keep them only if a consumer needs them.

### N2. The library is a second implementation that validates nothing [run]

It re-implements `Config::pick_spec`, `plan::assurance`, the feature default and the
`createOn` split. Evaluated against a lock with `version = 99`, an ID that is not an SRI and
a realisation naming another object, it returned all of it without complaint. `type.curve`
came back `"P-256"` where cakeys canonicalizes to `secp256r1`. A private key whose
realisation records no binding reads `assurance = "public"`.

`check`'s flags (`format`, `uriModule`, `uriPin`) are declared three times: clap,
`lib.nix` and `module.nix`.

**Recommendation:** shrink the view to what evaluation legitimately knows: `id`, `type`,
`requiredSystemFeatures` and `check`. Assert `lk.version == 1`. Pass `check` arguments
through as a list instead of enumerating them, so a new flag is one change.

### N3. The check command is not shell-escaped, and names have no grammar [run]

An object named `a b; echo pwned #` loads (C2) and the library returns
`… check a b; echo pwned # --token my token --spec s`. keys.toml is trusted, so this is a
robustness bug, not an exploit; the NixOS module escapes correctly
(`utils.escapeSystemdExecArgs`).

### N4. Two token namespaces joined by a string [read]

`services.cakeys.tokens.<n>` and keys.toml's `tokens.<t>` agree only through
`featurePrefix` (defined twice) or `systemFeature`. Nothing checks it. Low; say so in the
option's description.

## 3. keys.toml and keys.lock

The three tables (where, what, how) are the right split, and two boundaries are good closures
worth stating as such: the locator is exactly what an RFC 7512 URI can say about an object,
and policy is booleans plus one list. Neither boxes the design in. What does need attention:

### C1. Two specs can both create one object on one token [run]

`check_creation` dedups creating pairs by token name (`config.rs:1183-1186`), so two specs of
one object on one token, both `autoCreate`, with one locator and contradictory attributes
(`CKA_EXTRACTABLE = false` and `= true`), load. Whichever is realised first decides the
key's attributes; the other then conflicts (13). `createOn` promises that "where material is
born is never decided by which pair runs first"; with what policy it is born still is.

**Recommendation:** with `autoCreate` gone (V2) nothing marks the creating spec, so `create`
without a spec name refuses an object that several specs realise on one token, naming them;
`create <spec>` picks. `createOn` keeps naming the token.

### C2. Names have no grammar [run]

Object, spec and token names take any TOML key. `check` splits its reference on `.id.`, `gc`
prints `realisations.<spec>.<token>`, the lock nests tables by name, and the Nix library
builds shell from them. **Recommendation:** `[A-Za-z0-9][A-Za-z0-9_-]*` at load (17), before
keys.toml's keys freeze.

### C3. The core schema carries every tool's settings [read]

`TokenCfg` holds reach (`module`, `tokenLabel`), credentials, quirks (`provider`,
`profiles`, `options`), caprobe's `scratch` and `scratchId`, camigrate's `transportWith`
and Nix's `systemFeature`; `SpecCfg` holds camigrate's `noExport`. With
`deny_unknown_fields` and frozen keys, every tool feature is a core schema change.
`mgmKeyFile` is PIV vocabulary for what camigrate uses as any module's SO PIN.

**Recommendation:** before the freeze, namespace them the way `options` already is
(`tokens.<t>.probe`, `.migrate`, `.nix`), and rename `mgmKey*` to `soCredential*`.

### C4. `provider` means four things [read]

A code provider, a profile family, one exact profile (`aws-cloudhsm/5.18+hsm2m-non-fips`)
or `generic`. The exact-profile pin is how a non-FIPS cluster is told apart, smuggled through
the provider name. **Recommendation:** a separate `profile` key for the pin.

### C5. A token is selected by label alone [read]

`tokenLabel` is the only selector, while the lock's URI already carries the serial. Two
tokens with one label are 12 with no way to choose. **Recommendation:** an optional
`tokenSerial`.

### C6. The object type is a product of options [read]

`ObjectCfg` is `class` plus five optional fields, with the valid combinations checked
elsewhere. Post-quantum parameter sets, Montgomery curves and `CKK_DES2` each add a field and
cross-field rules. **Recommendation:** parse once at load into an enum; the TOML and the spec
digest stay as they are.

## 4. Capability profiles and providers: boxed in?

Yes, as aimed today. The evidence:

- **The denominator is the specification.** `profiles/coverage/cakeys.toml` gives each of
  1,097 PKCS#11 3.2 rows a status: 177 used, 831 out of scope, 79 gaps, 10 profile-only.
  Three quarters of the ledger is hand-written rules saying a row does not matter, and the 79
  gaps are a backlog OASIS defined.
- **The schema grows one field per quirk and does not converge.** `derive.sealed`,
  `derive.key-attribute`, `derive.read-only`, `wrap.oaep`, `decrypt.oaep`,
  `unwrap.refuse`, `generate.by-name`, `migration.secret-unwraps`, `trusted-wrap`. What
  has no field goes to `[notes]` under ad-hoc keys (`derive.template`,
  `template.public.CKA_PRIVATE`, `derive.destroy`, `purpose-bound`), which code cannot
  read and re-discovers at run time.
- **So does the `Provider` trait.** Of 18 hooks beyond `name` and `matches`, 11 have exactly
  one implementor and 2 have none (`mechanisms`, `migration`). Seven modules produced them.
- **A capability is not a property of a mechanism name.** It depends on the key, the
  parameters, the operation, the session, the client's configuration and the device's mode.
  kmsp11 already does not fit ("each mechanism works on some key", so its failures are notes
  and `Provider::generation` holds the truth). FIPS and non-FIPS CloudHSM tie on every match
  key. CloudHSM's `ecdh_without_kdf` changes what a probe measures and appears nowhere.
- **The matrix is unbounded:** module version × hardware × firmware × mode × client
  configuration, each cell needing hardware in hand. Nine profiles for seven modules so far.

None of that would matter if a profile were only a prediction. It is not:

### P1. A missing profile is fatal at every token open [run]

`resolution::choose` errors when a family has several profiles and none records the module's
version (`resolution.rs:237`), and `Token::open` maps that to 17 (`token/mod.rs:231`).
Reproduced:

```text
softhsm 2.8:      Ok, profile Some("softhsm/2.7")
aws-cloudhsm 5.19: Err: several module profiles for 'aws-cloudhsm' (…) and none records module version '5.19'
tpm2-pkcs11 1.11:  Err: several module profiles for 'tpm2-pkcs11' (…) and none records module version '1.11'
kmsp11 1.10:       Err: several module profiles for 'kmsp11' (…) and none records module version '1.10'
```

A client library update therefore refuses `check` in production until someone probes, and
the remedy the message names, `caprobe probe`, opens the token through the same function. A
family with one profile only gets a note, so committing a second profile for a family is what
arms this. `gate.rs:61` already treats the same condition as "not a config error".

### P2. Profile rows choose protocols [read]

`subtract` and `add` filter the mechanism list at open, and `derive.sealed` picks the
`pop-ecdh` variant (`possession.rs:188`). On hardware no profile covers, the row is cleared
to unknown and the sealed path is tried; a module that needs the other one fails rather than
falling back.

### What to describe instead

1. **Describe cakeys, not the module.** The questions cakeys ever asks are finite: can this
   token compute each identity scheme, make each proof, generate each type, perform each move
   method. A capability is one of those, answered yes, no or unknown with evidence. The probe
   is cakeys running its own operations on scratch, which is complete by construction. The
   PKCS#11 baseline stays as a dictionary of names.
2. **Unknown means try.** No profile is ever required to open a token. Where a row picks a
   protocol, the absent row means try the strong form and fall back. A profile's *no* stays a
   refusal: that is what saves a wasted key.
3. **Stop the trait growing.** Hooks stay for two things: repairing a report to what a
   compliant module would say (`ec_point`, `key_type`, `policy_flag`) and reaching outside
   PKCS#11 (`attest`, `import_plaintext`). Facts with one implementor become data
   (`manages_as_so`, `keeps_destroyed_keys`). Delete the two unused hooks.
4. **Demote the spec ledger from a gate to a report.** Keep the trace and the "used" list.
   The object matrix is different: it is measured against what cakeys identifies, so it stays.

### Keeping providers and the probe implementable

The test of the design is one question: **could this provider have been written outside the
tree?** `crates/cli/examples/custom-provider.rs` promises it. The last three say no:

| Commit | Provider | Generic source files changed |
|---|---|---|
| `0c74dd6` | kmsp11 (probing) | 4, with 172 lines in `caprobe/src/probe.rs` |
| `ac9b489` | kmsp11 (generating) | 6 |
| `7d614b3` | aws-cloudhsm | 14, in `core`, `profile`, `pkcs11`, `caprobe` and `camigrate` |

Four causes, each with its own fix:

1. **The probe is a second implementation of the verbs.** `probe.rs` drives the raw session
   with its own templates and its own sign, derive, decrypt and wrap code (1,500 lines beside
   `token/generate.rs`, `token/possession.rs` and camigrate's `sealed.rs`). So each quirk is
   taught twice, and the trait shows it: `generation` for the verbs and `bound_keys` for the
   probe are one fact about kmsp11; `stand_in` and `stand_ins` one fact about CloudHSM.
   *Fix:* the probe calls the verbs' own operations on scratch: create this type, compute this
   scheme, make this proof, move by this method. A provider that makes the verbs work has made
   the probe work, and `bound_keys`, `stand_ins` and `scratch_occupant` go.
2. **Hooks are point corrections inside generic code,** so a quirk at a point with no hook
   needs a new hook and an edit where it is called. *Fix:* close the trait at two kinds of
   seam and nothing else:
   - *repairs*, where a module's answer is made what a compliant module's would be: one for
     an attribute read (today `ec_point`, `key_type`, `policy_flag`), one for a mechanism
     (`stand_in`);
   - *operations*, which a provider may replace whole, the default being plain PKCS#11:
     create, destroy, import, attest. `generation`, `check_create`, `manages_as_so`,
     `keeps_destroyed_keys` and `import_plaintext` become the inside of an override.

   A provider that seems to need a new hook then overrides an operation in its own crate.
3. **Every profile fact has its own field, written in five places:** the struct in
   `profile.rs`, the hand-written emitter (`emit.rs`, which matches taplo's layout byte for
   byte), `diff.rs`, the probe, and the consumer. *Fix:* one row type,
   `<capability> = { answer, evidence, via }`, where a capability names an operation of
   cakeys (a scheme, a proof per key type, a generation per type, a move method per
   direction). A new capability is an enum variant and the operation that tests it; emitter,
   diff and algebra never change. *How* an operation succeeded (the sealed or the extractable
   ECDH, which OAEP hash, a read-write session) is the operation's own fallback order, with
   the variant that worked recorded in `via` as a hint. That replaces `derive.sealed`,
   `derive.read-only`, `decrypt.oaep`, `unwrap.refuse` and the `[notes]` that code cannot
   read.
4. **Profiles are keyed by what this repository can own hardware for.** *Fix:* the measurement
   belongs to the deployment. A token's answers are recorded beside its observation in the
   lock (which already holds its mechanism list), by `caprobe probe` and by every `realise`,
   which has just run a scheme and a proof on a real key. The mode and the client
   configuration are then covered without being named. Shipped profiles become priors for
   `validate` before first contact; an exact observation match uses them, anything else
   answers unknown, and nothing is fatal.

**Where "unknown means try" stops.** It holds for what can be undone or leaves nothing:
schemes, proofs, session objects. It does not hold for a creation on a token that may not be
able to delete (ykcs11 keeps the key; Cloud KMS keeps the label for good), nor for anything
that can spend a PIN retry. Those few facts must be known before the attempt, so they are
declared by the provider's operation (its `destroy` says it cannot), and an unknown there
refuses outside a scratch token. The planner in camigrate also still needs an answer without
touching the target: there, unknown is printed as unknown, and the dry run says it will try.

**Order.** (a) Collapse the hooks into the two repairs and four operations, with no change of
behaviour: the existing suites verify it. (b) Rewrite kmsp11 and aws-cloudhsm against that
trait touching nothing outside their crates; if that fails, the trait is still wrong, and it
is cheaper to learn now than at the next vendor. (c) Point the probe at the operations and
compare its answers with the committed rows. (d) The single row type. (e) Per-deployment
answers in the lock. Each step stands alone; (a) and (b) alone stop the spread.

## 6. Open questions

Answered 2026-11-15: nobody relies on a build creating the key (creation goes out of band);
`realise` re-recording is deliberate, as a lock file's (V2); nothing outside this repository
depends on the exit codes or keys, so 6 and 8 rename in place.

Still open:

- **V1's AK finding is read, not run.** It needs a swtpm case to confirm before the docs are
  corrected either way.
- **Where the Attestation Key is provisioned** (V2): `realise` for now. A swtpm case that
  evicts the AK, attests again and compares the root would show the key is the same one.
- **The `[migration]` rows stay as they are** (decided 2026-11-15): module-shaped and
  hand-written. camigrate's planner often cannot open the token it plans for (the lock alone,
  a transport file), its facts are pairwise and per key type, and a failed attempt must never
  fall back to a weaker exposure, so "unknown means try" does not apply to it. Retest after
  the other refactors, then decide whether measured per-direction rows make sense. Planning
  from the lock drops a profile-resolution error (`camigrate/src/tokens.rs:52`) [read], so
  plan item 1 matters to it too.
