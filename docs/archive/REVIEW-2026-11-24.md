## The answer in one paragraph

The test suite detects **change**, not **error**, and the review loop feeds it instances, not classes.

- **Instance fixes.** Each review writes findings as `file:line` instances. Each fix closes that instance and adds a test that pins the reported input. 85% of audited fixes had a test, but only 11% of those tests cover the class. 88% of fixes had a sibling, an incomplete fix or a recurrence found later.
- **Rules at call sites.** Rules are enforced where a caller remembers them, not in the operation or a type. So every new path and every fix is another place to forget one.
- **Self-generated oracles.** Expected values come from the code under test: golden tables, profiles written by the probe, fault tests that pin the current answer.
- **Liars modeled on demand.** A lying module is modeled only for the liar a past finding named.
- **Invisible gaps.** Gated suites skip green, and no runner counts tests. So untested behaviour looks tested, and 8 deleted tests went unnoticed.

The result is that **review-fix code is now the main source of new defects:**

- 45% of the Rust at HEAD was last written by a review-fix commit.
- 87% of today's findings cite such lines.
- 35 of today's 54 findings (65%) are in or about a prior fix.
- 16 of the 29 re-checked medium-or-higher 11-23 fixes (55%) did not hold.
- 83% of today's findings are in code the 11-23 review read and passed (F §5, §6).
- The 2026-11-18 review had already named the biggest class (rules in planners, not at the write) and its class fix. Only the instances were fixed, and 14 more instances have been found since.

## Root causes, ranked by evidence

### 1. The fix protocol closes instances, never classes

Evidence:

- **F §2.1, n = 41 audited fixes:**
  - 85% added a test, but only 11% of those tests cover the class.
  - 97% would fail if their fix were reverted.
  - Even so, 88% had a later sibling, incomplete fix or recurrence.
  - The 11-18 round is the control case: 100% tests, each checked red first, and 10 of 11 still have later siblings.
- **F §1.4:** 17 sibling chains, 16 of which reach 11-23 or today.
- **Today:** about 20 prior fixes are instance-only and 1 is wrong:
  - D-1: C-1's test swaps `object`, keeps `token`.
  - B-1, B-2, D-2: B-3's placement rule is on 2 of 4 paths.
  - E-2: D-4 changed 2 of about 20 "error → no" sites.
  - A-5: A-2's fix is bypassed by spelling the locator differently, and over-refuses a documented use.
  - Also A-7, A-9, B-10, B-12, C-10, D-5, E-3, E-4, E-8.

Why:

- A finding arrives as a location and an instance fix.
- The fixer implements the literal finding, and its regression test mutates exactly the reported field.
- Nothing requires a sibling search or a test over the rule.
- No prior review asked "why did no test catch this?". Only today's criteria did.

### 2. Rules live at call sites, not at the operation or in types

Classes D-MULTIPATH, D-PARALLEL and D-SEAM each appear in **6 of 6** reviews (F §1.2).

- **Dry-run plans:** the dry-run plan is a hand-written mirror of the write-time checks (D-2, D-3, D-4, D-6). The 11-23 plan item "dry run and real run share one entry" became a file split.
- **Rules repeated per site:**
  - Placement is asked on 2 of 4 paths (B-1, B-2).
  - The private-object rule is re-derived at 4 sites (B-4).
  - Delete's "really gone" knowledge lives in ykcs11 and a profile row, not in `ops::delete` (B-13).
  - The A-3 chain rules run inside `chain_to_anchor` only (A-7).
- **Tables restated across the core and profile crate boundary:** A-8, A-9.
- **Two sources for one decision:** module detection in code vs profile data (B-10).
- **Provider hooks default to "nothing":** what an override does or returns is never checked (B-2, B-3, B-7, B-8).

### 3. Fail-open: absence, error or "unknown" becomes a verdict

This is the largest class: 49 of 265 hand-classified prior findings, present in 6 of 6 reviews, and as large on 11-23 as on 11-11 (F §1.2).

Today's instances:

- **E-2:** about 20 probe sites record a device error as the module's "no". The committed ykcs11 profile has 10 such rows, and camigrate plans by them.
- **E-4:** an unverifiable check reads "yes".
- **A-9:** no data reads "no".
- **D-7:** `Option<bool> == Some(true)` reads an unknown flag as permitted, so data goes into a bundle in clear.
- **B-13:** `delete` trusts `CKR_OK`.
- **D-1, D-8, D-10:** fields of untrusted files are used as authority.

Why: no type carries *Unknown*, *Unverified* or *Claimed-by-untrusted-input*, so every site decides ad hoc. A row cannot say whose answer it is or how it was checked (E root cause 3).

### 4. Tests detect change, not error (oracles from the code under test)

- **Golden tables:** regenerated in the same commit as the behaviour, 36 of 47 times (C-8).
- **Hand-edited golden files:** fcaa6aa hand-edited 244 lines of `spec-coverage/objects/*`.
- **Profiles:** the probe writes the profiles and the conformance test compares the probe with them (E-7).
- **Bug pinned as spec:** `caprobe/tests/fault.rs:212-217` asserts that `CKR_DEVICE_ERROR` is the module's "no" (E-2).
- **Exit code or prose only:**
  - 39 of 131 harness tests assert only an exit code or prose (C-9).
  - Lock invariants are asserted as exit 17, which every lock rule returns (A root cause 6).
  - The dry-run twin accepts any 10 or 13 after a dry 0 (D-3).
- **Mutation testing:**
  - The only mutation run on record (11-15) left 27% of core's mutants alive.
  - `packages.mutants` excludes pkcs11, cli, caprobe and the providers, where most of today's findings are, and it gates nothing (F §3.3, C matrix).

### 5. The adversary is modeled per past finding, not systematically

- **The lie table:** it covers 3 verbs × 1 class of lie (C-6).
- **Never modeled:**
  - a destroy that answers OK and keeps the key (B-13),
  - a lying vendor certify or a TPM interposer (B-12),
  - a forged PIV slot certificate (B-11),
  - a source that hands over another key (D-5),
  - a hidden flag (D-7),
  - a corrupted blob the module still accepts (E-3).
- **Why it matters:** checks that matter only against a liar have no failing test, so they are the ones dropped from new paths (D root cause 5).
- **The tooling is there:** p11-fault can already model more liars than any test uses (B root cause 4).

### 6. What is not verified is invisible

**The hardware constraint is real and accepted: not every merge can run the hardware suites.** The problem is that nothing records what was *not* verified:

- **Silent skips:** every gated test skips and passes.
- **Fault-suite routing:** the fault suites' `*_REQUIRE` variable is set by the same routing it guards (C-11).
- **No count:** no runner counts tests, so 8aaba2e's "verbatim" split deleted 8 core tests unnoticed (A-1). Docs still cite three of them.
- **Fixes whose tests run only when gated:** 37% of fix tests fail on a revert only when a token, swtpm or VM suite runs (F §2.1).
- **Integration tests:** about 82% need tokens, swtpm or hardware, and skip and pass under plain `cargo test`.
- **Commit messages:** 84% say nothing about what ran (F §4).
- **Hardware and cloud profiles:**
  - 6 of 9 module profiles are re-derived by no automated run, yet were hand-edited by three review-fix commits.
  - Their header says "Never edit … re-probes on every build" (E-7).
- **Shipped build:** `packages.default` is built by no check (C-10). `tpm2` is not compiled on darwin.
- **CI** (lead-verified, GitHub API):
  - 12 of the last 23 `checks` runs on main are green.
  - Main has been red since 38967ae (2026-11-19).
  - Both jobs that fail at HEAD, `checks-no-vm` and `checks-vm`, **need no hardware**. C-3 names two checks that fail from reading the code.

### 7. Docs are the spec, and nothing checks them

Universal claims are written, believed, and used to judge fixes:

- "every host path", "the one way" and "for the file's token" (D-1, D-5),
- "unknown, never yes" (E-4),
- "never touches PIV data objects" (E-6),
- "a rule change fails `lock_mbt`" (A-6),
- the ISSUES.md "fixed" entry for YubiHSM detection (B-10).

`checks.doc-references` reads Markdown only (A-2).

### 8. The review process cannot see these classes

- Every prior review was read-only, and only 11-15 ran anything (F §1.1).
- Reviews are split by area, so a cross-path rule falls between reviewers. B and D found the same placement gap from two sides (B-1, D-2).
- No review before today checked CI, ran a fix, counted skips, or asked which test fails if a decision is flipped.
- Scope grows faster than the review-fix loop: 461 commits and about 182k added lines in 11 active days. The two days after the 11-13 review added about 14k lines of new subsystems (F §3).
- 383 of 461 commits are co-authored by Claude models. The writer and the reviewer share blind spots, and each review is mostly a fresh read rather than a check against executable evidence.
- Today's ~120 unguarded decisions were found by hand. That is the job a mutation tool does mechanically.

## Plan

The plan is ordered by leverage per cost. It assumes hardware stays scarce, so every step moves verification *off* hardware or makes its absence visible. None of it adds a hardware run per merge.

### Phase 0: make the gate honest (days)

1. **Tiered gate, written down** (DEVELOPMENT.md and CI):

   | Tier | What | Required |
   |---|---|---|
   | T0 | build, unit tests, software tokens, liar matrix, doc checks, test-count check | before every merge |
   | T1 | Linux VM checks; needs no hardware | before merge, or within 24 h of merge with fix-forward |
   | T2 | YubiKey, fTPM and cloud | scheduled or manual; results recorded per commit |

   Bring `light` and `vm` back to green first (C-3; restore the 8 tests from A-1). Neither job needs hardware, so F recommends making both required checks in branch protection. The hardware tier stays out of the merge path.
2. **Count the tests.**
   - Each runner emits the number of tests run and skipped per suite (nextest JUnit).
   - A committed manifest sets a minimum per suite.
   - A drop fails unless the manifest changes in the same diff.
   - Required suites fail on zero tests.
   - A fault suite's require variable is set apart from its routing (C-11).
3. **Verification ledger for hardware-derived data.**
   - Each hardware profile and golden table records the commit and date it was last *probed*.
   - A T0 check warns when code on that hardware's path has changed since.
   - Fix the "re-probes on every build" header (E-7).
   - A hand edit to generated data must say so in a field the check reads.
4. **Fix protocol** (in DEVELOPMENT.md and the review criteria). A finding closes only with:
   - (a) the class named;
   - (b) the sibling search recorded (the `rg` used and the hits);
   - (c) a test over the *rule* across every entry path, seen failing first;
   - (d) T0 green.

   Reviews report classes with sibling lists, and fixes go by class, using the table below.

### Phase 1: put rules where they cannot be skipped (1–2 weeks)

5. **One plan-then-execute path per operation.**
   - `plan(op) -> Plan` runs every rule: identity, transport binding, placement, locator free, private object, extractability.
   - `execute(Plan)` performs it. `--dry-run` prints the `Plan`.
   - No rule lives outside `plan`. The twin's oracle becomes exact: same exit unless the device fails.
   - This closes D-2, D-3, D-4, D-6, B-1, B-2, B-4 and the 11-18 class.
6. **Types for trust and knowledge.**
   - `Claimed<T>`, for values from untrusted files and modules, becomes `Verified<T>` only through a check (D-1, D-8, D-10).
   - A tri-state `Known` replaces `Option<bool>` for restrictions (D-7).
   - Probe rows carry provenance: module-refused, cakeys-refused, device-failed, host-verified, unverified (E-2, E-4, E-5). `rv::device_failed` becomes public for caprobe.
7. **Provider seam contract.**
   - Hooks return typed decisions, and a missing hook means refuse or unknown, not "nothing".
   - One contract test runs every provider through the same cases, data providers included (B-2, B-3, B-7, B-8).
8. **One source for shared tables.** Move the restated tables (mechanisms, curves, proof names, commitment kinds) into a leaf crate that both core and profile depend on, or generate them (A-8, A-9).

### Phase 2: oracles independent of the code, adversary by table (2–3 weeks)

9. **Liar matrix.**
   - A table of verb × lie, run through p11-fault on software tokens in T0/T1.
   - Lies: OK-without-effect on destroy and login; another key handed over; a flag hidden or flipped; a value that changes between reads; a forged vendor certify; a corrupted blob the module accepts; a device error vs a refusal.
   - A lint fails when a security check has no liar row that makes it fire.
   - This closes B-11, B-12, B-13, C-6, D-5, D-7, E-3 and E-6 as a class.
10. **Hardware personas by record and replay.**
    - When hardware is at hand, capture p11-fault traces of the YubiKey, fTPM, CloudHSM and Cloud KMS runs.
    - Replay them as personas in T0.
    - Hardware is then needed only to *refresh* a persona, not for each change to code on its path.
11. **Independent oracles.**
    - Every "yes" in a probe row is verified on the host, or it is recorded as unverified.
    - The regen scripts diff before they overwrite.
    - A commit that changes both logic and golden data must list the changed rows and say why each is right (a check on the commit or PR).
    - The harness gets `assert_unchanged(token, lock)` and asserts structured rule IDs in JSON, including on failures, instead of prose (C-9).
12. **Docs as tests.** Extend `doc-references` to Rust doc comments (A-2). Each universal claim in DESIGN, CAMIGRATE and CAPROBE gets a cross-path test, or the doc is softened.

### Phase 3: mutation testing as the standing review (ongoing)

13. **Run `cargo-mutants` in the Linux T0 or T1 tier.**
    - Run `--in-diff` on the files a change touches.
    - Cover core (reconcile, check, chain), pkcs11 token operations, camigrate (plan, tokens, host), caprobe rows and the providers' attestation.
    - Commit a baseline of surviving mutants that may only shrink. Run in full weekly.
    - This mechanizes the ~120 hand-found unguarded decisions. Reviews then start from the survivors instead of a fresh read.

### Verification that the plan works

- The surviving-mutant count falls release over release.
- The test-count manifest never drops silently.
- The next review's fix audit (F §2.1 method) shows class-level tests above 80%, and its sibling rate falls below today's 88%.
