## Rules

- Do not run cargo, nix builds or tests (user rule: no long builds). Never search `/nix/store`.
  git (log, blame, show, grep), rg/grep, and reading files are fine and encouraged: use
  `git log -L`/`git blame`/`git log -S` to find when a line arrived and whether a test came with it.

- Known open items in `docs/OPEN.md` and decided items in `docs/archive/REVIEW-2026-11-23*.md` are
  not new findings. But a prior fix that is wrong, incomplete, or fixed only the reported instance
  while siblings remain **is** a finding, and is strong root-cause evidence. Say which prior ID.
- **Write as you go.** Create your file first with the skeleton below, then append after *each
  file* you finish (`cat >> FILE <<'EOF'` … `EOF`, quoted heredoc). Never hold findings until the end.

## How to review each file

1. Read the file in full, with its tests (inline `#[cfg(test)]` and any `tests/` file that targets it).
2. Correctness and security as before: PKCS#11 semantics (CK_RV, two-call reads, sessions, login,
   handles), lying/hostile token or module or file, exit codes, failure/rollback paths, panics on
   untrusted input, secret handling, TOCTOU, docs-vs-code.
3. **Mental mutation testing (required).** For each security- or correctness-critical decision in
   the file (a comparison, a guard, a refusal, an early return, a match arm, a default), ask: *if I
   flipped or deleted this, which test fails?* Find that test (rg for the function / error / exit
   code). If none would fail, that is a **test gap** finding even if the code is right today. Record
   these in the file's "unguarded decisions" list: `path:line — decision — no failing test because …`.
4. **Entry-point audit.** For each rule the file enforces, list every path that reaches the same
   operation (real run, `--dry-run`, gate/validate, probe, migrate, other tool, other provider).
   A rule enforced on some paths only is a finding (prior examples: B-3, C-2).

## Every finding must carry

```text
### <X>-<n>. <title> — <critical|high|medium|low> — <verified|plausible>
`path:line[-line]`
What: the triggering input/state and the consequence.
Why missed: <escape codes, below> — the concrete reason: which test should have caught it and why
  it did not (does not exist / skips without hardware / asserts the wrong thing / the fixture is
  generated by the code under test / only the reported instance was tested / …). Use git blame/log:
  was it introduced by a "review fix" commit? Did that commit add a test? Would that test fail if
  the bug came back?
Class: the general pattern, and other instances of it you found (rg the repo). Count them.
Instance fix: … Class fix: the structural change that makes the whole class impossible or caught.
```

## Escape-cause codes (use these; add new ones with a definition if none fit)

| Code | Meaning |
|---|---|
| T-ABSENT | No test reaches this path at all. |
| T-ORACLE | A test reaches it but asserts the wrong thing: exit code only, prose, "no error", a count, not the result. |
| T-TAUTO | Expected value comes from the code under test (fixture generated by it, same helper on both sides). |
| T-GATED | Test exists but skips or is not run: needs a token, hardware, cloud, platform, a feature, nextest vs cargo test, not in CI/`nix flake check`. |
| T-FRIENDLY | Only well-behaved reference tokens/modules/files exercise it; the hostile or odd case is never modeled (p11-fault, crafted DER/TOML, lying module). |
| T-INSTANCE | A regression test exists for the reported instance only; siblings of the same class are untested. |
| D-MULTIPATH | The rule is enforced on one entry path; other paths (dry-run, gate, probe, migrate, provider override) re-implement or skip it. |
| D-PARALLEL | Hand-synced parallel tables, enums, lists, or docs that must agree and drifted. |
| D-TYPES | An invalid state is representable (stringly typed, bool/Option soup, unchecked constructor); validity lives in call-site discipline. |
| D-SEAM | Abstraction with an unclear contract: the trait/hook's default or override changes semantics silently. |
| D-DOCS | Docs or comments assert a guarantee the code does not provide, and nothing checks the claim. |
| P-UNRUN | Fix was written without building/running (prior reviews did this), so its test never failed red or passed green. |
| P-REVIEW | Prior review read this file and missed it: say why (scope, depth, criteria did not ask). |

## Severity

- critical: identity / possession / attestation check can be fooled, secret leak, key or lock data loss.
- high: wrong result, crash, or misleading success reachable by a user in normal use.
- medium: latent bug, confusing or inconsistent behaviour, unguarded critical decision.
- low: nit, small inconsistency.
