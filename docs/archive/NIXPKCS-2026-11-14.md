# nixpkcs: what cakeys can use (2026-11-14)

A survey of [numinit/nixpkcs](https://github.com/numinit/nixpkcs) at `a911f13` (v1.3.1),
cloned to `~/srcs/nixpkcs`: an overlay (`overlay.nix`), a NixOS module (`module.nix`,
`security.pkcs11`), a bash key generator (`nixpkcs.sh`) and two VM tests (Nebula, nginx), about
2 600 lines in all.

**Short answer.** Almost no code to take; a handful of module facts, one consumer recipe and two
test shapes worth having, all pointing at work already planned (PLAN.md S1/B1, OPEN.md "The
contract with programs", "More reference tokens").

**License.** nixpkcs is LGPL-3.0 (`COPYING.md`); cakeys is MIT OR Apache-2.0. "Use" below means
one of: depend on it as a flake input, take a fact or an idea, or take the upstream original it
wraps. Copying its Nix or bash into the tree is out, as PRIOR-ART.md says of Sequoia.

## What it is

nixpkcs generates keys: per `security.pkcs11.keypairs.<name>` a daily oneshot
`nixpkcs@<name>` runs `pkcs11-tool --keypairgen` at a `(token, id)`, self-signs a certificate
with `openssl req -provider pkcs11 -key <uri> -x509`, writes it back with
`pkcs11-tool --write-object --type cert`, and renews it near expiry (off by default since 1.3).
The certificate is its "record" of the key. The overlay adds `pkcs11Module` passthrus
(`{ path, openSslOptions, mkEnv, storeInit, noLabels }`) to tpm2-pkcs11, yubico-piv-tool,
opensc, yubihsm-shell and nss_latest, and `withPkcs11Module` wrappers to openssl and opensc.

cakeys records and verifies what is on a token; nixpkcs makes it. They overlap only where both
touch Nix, URIs and modules.

## Usable

Each item ends where the repository's convention puts findings: a test, a profile row, a fix or
an OPEN.md item.

### 1. An OpenSSL config for pkcs11-provider (PLAN.md S1, B1)

`openssl.withPkcs11Module` (`overlay.nix`) writes an `OPENSSL_CONF` that `.include`s the stock
config, activates the default provider and loads `${pkcs11-provider}/lib/ossl-modules/pkcs11.so`
with `pkcs11-module-path` and `pkcs11-module-encode-provider-uri-to-pem = true`, then wraps every
binary of a package (`symlinkJoin` + `wrapProgram --set OPENSSL_CONF`). The nginx test wraps
nginx itself (`confName = "nginx"`) and serves TLS from a TPM key.

S1 asks whether `ukify` signs with a `pkcs11:` key through pkcs11-provider in the sandbox, and
B1's signer needs the same. What matters is about ten lines of openssl.cnf: write them in the
test, rather than depend on nixpkcs' overlay and its nixpkgs pin. **Ends as:** part of S1.

### 2. Module quirks for pkcs11-provider (candidate profile rows or test settings)

From the `openSslOptions` of each `pkcs11Module`, unverified here; check the names against the
pkcs11-provider version B1 pins:

| Module | pkcs11-provider options nixpkcs sets |
|---|---|
| tpm2-pkcs11 | `pkcs11-module-quirks = no-operation-state` |
| ykcs11 | `pkcs11-module-login-behavior = never`, `quirks = no-deinit no-operation-state`, `cache-pins = cache` |
| yubihsm_pkcs11 | `quirks = no-deinit`, `cache-pins = cache` |
| opensc, NSS softokn | none |

Its changelog adds: pkcs11-provider's default early init broke the YubiHSM, fixed by lazy
(`auto`) init (1.3.0). **Ends as:** the B1 signer matrix's settings per token; a note in the
capability profile if a quirk turns out to be a module property rather than a provider setting.

### 3. Writing a certificate to a token (PLAN.md B1 step 1)

B1 step 1 is "create the three self-signed certificates with the token keys and store them as
`CKO_CERTIFICATE` objects": nixpkcs' `gen_key` does exactly that. One fact from it: since
OpenSC 0.26, `pkcs11-tool --write-object` cannot read `/dev/stdin`, so the DER goes through a
temporary file. **Ends as:** B1's provisioning script.

### 4. A PEM-wrapped URI for programs that only read PEM files

nixpkcs exposes `pkcs11-provider.uri2pem` (with a functor, `uri2pem "<uri>"` → a store path) and
the nginx test passes it as `sslCertificateKey`. The tool is pkcs11-provider's own
`tools/uri2pem.py`, so cite and take it from there (Apache-2.0), not from nixpkcs.

It matters for "The contract with programs" (CAKEYS.md, OPEN.md): many programs take a key
file, not a URI, and `cakeys check` prints a bare URI. A helper must keep the check in front: a
PEM made at evaluation time from the lock's `uri` (as `lib.mkKeys` exposes it) skips
verification. The shape that keeps it is a check unit that runs `cakeys check`, wraps its
output, and writes the PEM where the service reads it. **Ends as:** an OPEN.md line under
"The contract with programs".

### 5. URI questions for B1's four-parser test

- **ykcs11 and `object=`.** nixpkcs omits `object=` for ykcs11 (`noLabels`, changelog 1.1.4)
  because OpenSSL could not use its URIs. There the label in the URI was one nixpkcs had asked
  for, and ykcs11 assigns its own fixed labels per slot. cakeys' `uri.rs` puts in the label its
  locator found on the token, so this probably does not apply; the B1 parsers settle it.
  **Ends as:** a case in that test (a ykcs11 URI with `object=`, through pkcs11-provider).
- **Escaping `/`.** nixpkcs escapes it (`lib.escapeURL`), `uri.rs` does not. That is no evidence
  either way: PLAN.md's open question is decided by RFC 7512 §2.3's grammar.

### 6. NSS softokn as a reference token (OPEN.md "More reference tokens")

nixpkcs tests against `nss_latest`'s `libsoftokn3.so`: `certutil -N -d <dir>` creates the
store, `NSS_LIB_PARAMS=configDir=<dir>` points the module at it, the token is
`NSS Certificate DB` in slot 2. Its cryptography is NSS freebl, not OpenSSL, so unlike haskoki
it would be independent of kryoptic. How much of what cakeys uses it implements (secret-key
commitments, unwrap, Edwards keys) is unknown; a `caprobe probe` would say. **Ends as:** an
OPEN.md line next to haskoki.

### 7. A VM test that gates a real consumer

The nginx test starts a TLS server whose key lives in tpm2-pkcs11, with `extraEnv` passed to
the unit and `ProtectSystem`/`PrivateDevices` forced off so nginx reaches the TPM store and
device. `checks.module` today shows that a `cakeys-check-<n>` unit runs; it does not show that
a real service is held back by it. The same shape with
`services.cakeys.checks.<n>.requiredBy = [ "nginx.service" ]`, a swapped key and nginx not
starting would. **Ends as:** a VM test (or part of B1).

### 8. Serializing access to one module

nixpkcs takes `flock` on `/var/lock/nixpkcs-<hash of module path>.lock` before touching a
token. cakeys locks `keys.lock.lck` around lock writes only; nothing serializes concurrent
`check`s (several check units at boot, parallel builds) against one ykcs11 or pcscd token.
Whether that is a problem is untested. **Ends as:** an OPEN.md line under Engineering.

## Not used

- **Generation, renewal, `validStarting`, the self-signed certificate as record**: key
  generation policy and rotation are out of scope (README); the lock and attestation are
  cakeys' record.
- **`module-path=` and `pin-source=` in the URI**: PLAN.md decided the URI carries neither;
  the module goes through `lib.mkKeys`' `modules`, the PIN through a granted file.
- **The pcsc polkit rule**: cakeys' rule already covers build users (nixbld and auto-allocated
  UIDs) and returns `NOT_HANDLED` otherwise.
- **`nixpkcs-uri`**: `cakeys check` prints the URI, after verifying.
- **The tpm2-pkcs11 store init and environment**: `nix/tpm2-test-env.sh` already does
  `tpm2_ptool init`/`addtoken` and sets `TPM2_PKCS11_BACKEND=esysdb` and `TSS2_LOG`. nixpkcs also
  passes the PINs on `tpm2_ptool`'s command line, the open item cakeys has (OPEN.md, "Moving
  keys").
- **The Nebula patch, the integer-to-`%xx` ID encoder in Nix, the `mkEnv` passthrus**: nothing
  in cakeys needs them; `CKA_ID` is already hex in keys.toml and `uri.rs`.
- **yubihsm-shell's `YUBIHSM_PKCS11_CONF` generator**: only relevant with a YubiHSM provider,
  which there is none of.

## Using both on one host

nixpkcs makes and renews; cakeys pins. A nixpkcs keypair `(token, id)` is a cakeys spec with a
`CKA_ID` locator (and no `CKA_LABEL` on ykcs11), realised once; a later renewal then fails
`check` with 10, which is cakeys working as intended. Set `certOptions.renewalPeriod = -1` (the
default) and use `validStarting` for planned new keys.

One hazard to test before claiming they combine: nixpkcs' `share/polkit-1/rules.d/10-pcsc.rules`
returns `NO` for any user not in `security.pkcs11.pcsc.users`, nixbld included. polkit runs
rules files in name order across directories, so NixOS' `10-nixos.rules` (where
`security.polkit.extraConfig`, and so cakeys' `YES`, lands) should run first; a VM with both
modules would confirm it.
