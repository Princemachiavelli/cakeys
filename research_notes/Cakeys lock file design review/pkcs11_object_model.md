## Q1. Object classes and attributes in PKCS#11 3.0 / 3.1 / 3.2, classified by role

### Takeaway

PKCS#11 3.2 has eleven object classes, of which five are storage objects RFC 7512 can address and cakeys handles (data, certificate, public/private/secret key); 3.2 adds `CKO_TRUST`, `CKO_VALIDATION`, ML-DSA/ML-KEM/SLH-DSA/XMSS and several token-computed attributes. Every key attribute falls into one of five roles: intrinsic material, mutable policy, one-way lifecycle, token-assigned provenance, or informational locator (full table under Inferences).

### Cited Findings

**Object model basics**

- "An object consists of a set of attributes, each of which has a given value." Objects are "always well-formed". "A token can hold several identical objects, i.e., it is permissible for two or more objects to have exactly the same values for all their attributes." Objects may also carry vendor-specific attributes. — [3.2 §4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- Objects are created by these functions — [3.2 §4.1.1](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html):
  - `C_CreateObject`, `C_GenerateKey` and `C_GenerateKeyPair`;
  - `C_UnwrapKey` and `C_DeriveKey`;
  - `C_EncapsulateKey` and `C_DecapsulateKey` (new KEM functions in 3.2);
  - `C_CopyObject`.
- Create-time error rules — [3.2 §4.1.1](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html):
  - Read-only attributes in a template give `CKR_ATTRIBUTE_READ_ONLY`.
  - A token "may be even more restrictive than Cryptoki specifies".
  - Inconsistent templates give `CKR_TEMPLATE_INCONSISTENT`, which "is token-dependent".

- **`CKO_TRUST`** binds trusted usages to a certificate via `CKA_ISSUER`, `CKA_SERIAL_NUMBER`, `CKA_HASH_OF_CERTIFICATE` and `CKA_NAME_HASH_ALGORITHM`. Its usage attributes are `CKA_TRUST_SERVER_AUTH`/`CLIENT_AUTH`/`CODE_SIGNING`/`EMAIL_PROTECTION`/`IPSEC_IKE`/`TIME_STAMPING`/`OCSP_SIGNING`, with values `CKT_TRUSTED`, `CKT_TRUST_ANCHOR`, `CKT_NOT_TRUSTED`, `CKT_TRUST_MUST_VERIFY_TRUST` and `CKT_TRUST_UNKNOWN`. — [3.2 §4.7, Table 25](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **`CKO_VALIDATION`** objects "are read only, token objects". They carry the validation type, version, level, module ID, flag, authority (NIST CMVP / Common Criteria), country, certificate ID/URI and profile. — [3.2 §4.15, Table 34](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **What is new in 3.2.** A text search of the three documents finds the following in 3.2 only:
  - `CKO_TRUST`, `CKO_VALIDATION`, `CKA_OBJECT_VALIDATION_FLAGS`;
  - `CKA_PUBLIC_CRC64_VALUE`, `CKA_ENCAPSULATE`/`CKA_DECAPSULATE`;
  - `CKA_PARAMETER_SET` and `CKA_SEED` (ML-DSA/ML-KEM/SLH-DSA; `CKA_PARAMETER_SET` also for XMSS/XMSSMT);
  - `CKK_ML_DSA` and `CKK_XMSS` (0 hits in 3.1).

  HSS/LMS (`CKK_HSS`, with `CKA_HSS_LEVELS`/`CKA_HSS_LMS_TYPE`/`CKA_HSS_LMOTS_TYPE`) is already in 3.1, with the same hit counts in 3.1 and 3.2.

  Sources: [3.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html), [3.1](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.1/os/pkcs11-spec-v3.1-os.html), [3.0 base](https://docs.oasis-open.org/pkcs11/pkcs11-base/v3.0/os/pkcs11-base-v3.0-os.html).
- **Already present in 3.0 base:** `CKA_UNIQUE_ID` (13 mentions), `CKO_PROFILE`, `CKA_PUBLIC_KEY_INFO`, `CKA_COPYABLE`, `CKA_DESTROYABLE` and `CKA_ALWAYS_AUTHENTICATE`. — [3.0 base](https://docs.oasis-open.org/pkcs11/pkcs11-base/v3.0/os/pkcs11-base-v3.0-os.html)

**Common storage attributes (Table 19)**

- The attributes are `CKA_TOKEN` (default false), `CKA_PRIVATE` (default "token-specific"), `CKA_MODIFIABLE` (default true), `CKA_LABEL` (default empty), `CKA_COPYABLE` (default true; "Can't be set to TRUE once it is set to FALSE"), `CKA_DESTROYABLE` (default true) and `CKA_UNIQUE_ID` (footnotes 2,4,6). — [3.2 §4.4, Table 19](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- "Only the CKA_LABEL attribute can be modified after the object is created." `CKA_TOKEN`, `CKA_PRIVATE` and `CKA_MODIFIABLE` can be changed while copying. — [3.2 §4.4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- `C_CopyObject` may also change `CKA_DESTROYABLE`. The four "special" attributes are TOKEN, PRIVATE, MODIFIABLE and DESTROYABLE. — [3.2 §4.1.3](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- `CKA_COPYABLE` "can be used in conjunction with CKA_MODIFIABLE to prevent changes to the permitted usages of keys". — [3.2 §4.4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)

**Common key attributes (Table 26)**

| Attribute | Footnotes / semantics |
|---|---|
| `CKA_KEY_TYPE` | 1,5 |
| `CKA_ID` | 8 |
| `CKA_START_DATE`, `CKA_END_DATE` | 8 |
| `CKA_DERIVE` | 8 |
| `CKA_LOCAL` | 2,4,6 |
| `CKA_KEY_GEN_MECHANISM` | 2,4,6 |
| `CKA_ALLOWED_MECHANISMS` | No footnote 8, so not modifiable per spec |
| `CKA_OBJECT_VALIDATION_FLAGS` | 4,6,9,12 (3.2) |

Semantics from the same section:

- Dates are "for reference only; Cryptoki does not attach any special meaning to them".
- `CKA_LOCAL` is true "if and only if the value of the key was originally generated on the token by a C_GenerateKey or C_GenerateKeyPair call", or it is a `C_CopyObject` copy of such a key.
- `CKA_KEY_GEN_MECHANISM` is valid only if `CKA_LOCAL` is true; otherwise it is `CK_UNAVAILABLE_INFORMATION`.

Source: [3.2 §4.8.2, Table 26](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**Public key attributes (Table 27)**

- Usage and type: `CKA_SUBJECT`, `CKA_ENCRYPT`, `CKA_VERIFY`, `CKA_VERIFY_RECOVER`, `CKA_WRAP` and `CKA_ENCAPSULATE` (all 8; usage bits also 9).
- Wrapping: `CKA_TRUSTED` (10) and `CKA_WRAP_TEMPLATE`.
- `CKA_PUBLIC_KEY_INFO`: "MAY be empty, DEFAULT derived from the underlying public key data".
- `CKA_PUBLIC_CRC64_VALUE` (1,4,13): "CRC-64-ECMA calculated over the public key object's CKA_VALUE attribute unless otherwise specified".

Source: [3.2 §4.9, Table 27](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**Private key attributes (Table 29)**

- Usage: `CKA_SUBJECT` (8), `CKA_DECRYPT`/`CKA_SIGN`/`CKA_SIGN_RECOVER`/`CKA_UNWRAP`/`CKA_DECAPSULATE` (8,9).
- Lifecycle: `CKA_SENSITIVE` (8,11), `CKA_EXTRACTABLE` (8,12), `CKA_ALWAYS_SENSITIVE` and `CKA_NEVER_EXTRACTABLE` (2,4,6), `CKA_WRAP_WITH_TRUSTED` (11).
- Templates and authentication: `CKA_UNWRAP_TEMPLATE`, `CKA_ALWAYS_AUTHENTICATE`, `CKA_DERIVE_TEMPLATE`.
- `CKA_PUBLIC_KEY_INFO` (8): "MAY be empty; … MAY be manually set …; if set, MUST be consistent with the underlying private key data".
- `CKA_PUBLIC_CRC64_VALUE` (1,4,13).
- If `CKA_PUBLIC_KEY_INFO` is supplied on `C_CreateObject`/`C_CopyObject`/`C_SetAttributeValue`, "the token MUST verify correspondence … If there is a mismatch, the command SHALL return CKR_ATTRIBUTE_VALUE_INVALID".
- `CKA_ALWAYS_AUTHENTICATE` "may only be set to CK_TRUE when CKA_PRIVATE is also CK_TRUE". Each use needs `C_Login(CKU_CONTEXT_SPECIFIC)` after the `*Init` call.

Source: [3.2 §4.10, Table 29](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**Secret key attributes (Table 30)**

- `CKA_SENSITIVE` (8,11; "default CK_FALSE"); the usage bits (8,9); `CKA_EXTRACTABLE` (8,12); `CKA_ALWAYS_SENSITIVE`/`CKA_NEVER_EXTRACTABLE` (2,4,6).
- `CKA_CHECK_VALUE`, `CKA_WRAP_WITH_TRUSTED` (11), `CKA_TRUSTED` (10), and the WRAP/UNWRAP/DERIVE templates.
- **KCV.** It is 3 bytes. It "should not be usable to obtain any part of the key value" and is non-unique. "If supported, … always supplied … even if … CKA_ENCRYPT is set to CK_FALSE".
- The application can suppress the KCV with a zero-length template entry. "C_SetAttributeValue may be used to destroy the attribute".
- The default KCV algorithm is "the first three bytes of an encryption of a single block of null (0x00) bytes".

Source: [3.2 §4.11, Table 30](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**Certificate attributes (Tables 21–22)**

- Common: `CKA_CERTIFICATE_TYPE` (1), `CKA_TRUSTED` (10), `CKA_CERTIFICATE_CATEGORY`, `CKA_CHECK_VALUE`, `CKA_START_DATE`/`END_DATE` and `CKA_PUBLIC_KEY_INFO`.
- `CKA_CHECK_VALUE` is "the first three bytes of the SHA-1 hash of the certificate object's CKA_VALUE".
- `CKA_CERTIFICATE_TYPE` and `CKA_CERTIFICATE_CATEGORY` "may not be modified after an object is created". `CKA_TRUSTED` "MUST be set by a token initialization application or by the token's SO. Trusted certificates cannot be modified".
- X.509 adds `CKA_SUBJECT` (1), `CKA_ID`, `CKA_ISSUER`, `CKA_SERIAL_NUMBER`, `CKA_VALUE` (2), `CKA_URL`, `CKA_HASH_OF_SUBJECT/ISSUER_PUBLIC_KEY`, `CKA_JAVA_MIDP_SECURITY_DOMAIN` and `CKA_NAME_HASH_ALGORITHM`.
- "Only the CKA_ID, CKA_ISSUER, and CKA_SERIAL_NUMBER attributes may be modified after the object is created."
- A certificate may hold only `CKA_URL` with an empty `CKA_VALUE`.

Source: [3.2 §4.6.2–4.6.3](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**PQ keys (3.2)**

- **ML-DSA public key** (`CKK_ML_DSA`): `CKA_PARAMETER_SET` (1,3) and `CKA_VALUE` (1,4), the "Public key as defined in [FIPS 204]". This is a raw encoding, not SPKI. — [3.2 §6.67.2, Table 280](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **ML-DSA private key:**
  - Attributes: `CKA_PARAMETER_SET` (1,4,6), `CKA_SEED` (4,6,7; ξ) and `CKA_VALUE` (1,4,6,7; sk).
  - "At least one of CKA_SEED and CKA_VALUE must be specified on C_CreateObject."
  - The parameter set is given in the *public* template on generation.
  - The generation mechanism contributes `CKA_CLASS`, `CKA_KEY_TYPE` and `CKA_VALUE` to the public key, and additionally `CKA_PARAMETER_SET` and `CKA_SEED` to the private key.

  Source: [3.2 §6.67.3–6.67.4, Table 281](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).
- **ML-KEM** has the same shape. `CKA_SEED` is "(d||z)". — [3.2 §6.68](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **SLH-DSA** public key: `CKA_PARAMETER_SET` and `CKA_VALUE` ("Public key as defined in [FIPS 205]"). — [3.2 §6.69.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **XMSS/XMSSMT** use `CKA_PARAMETER_SET` (§6.66).
- **HSS** instead uses `CKA_HSS_LEVELS`, `CKA_HSS_LMS_TYPE` and `CKA_HSS_LMOTS_TYPE` (2,4), with `CKA_VALUE` as the "XDR-encoded public key as defined in [RFC8554]" (§6.65.2).
- **Other key-type KCVs:** generic secret KCV = "first three bytes of the SHA-1 hash of the generic secret key object's CKA_VALUE" (§6.8.2). ChaCha20 also uses SHA-1. AES and other block ciphers use ECB of a zero block.

Source: [3.2 §6.8.2, §6.65–6.66](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

**Reading attributes (`C_GetAttributeValue`, §5.7.5)**

- An attribute that "cannot be revealed because the object is sensitive or unextractable" yields `CK_UNAVAILABLE_INFORMATION` and `CKR_ATTRIBUTE_SENSITIVE`. An attribute the object lacks yields `CKR_ATTRIBUTE_TYPE_INVALID`.
- These "do not denote true errors": the call "MUST nonetheless have processed every attribute in the template".
- Array attributes (templates) have `CKF_ARRAY_ATTRIBUTE` set.

Source: [3.2 §5.7.5](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).

### Inferences

**The five roles, in brief:**

| Role | Attributes |
|---|---|
| Intrinsic/material | class, key type, curve, modulus, parameter set, value |
| Mutable policy | usage bits, `CKA_ID`, dates |
| One-way/lifecycle | `SENSITIVE`, `EXTRACTABLE`, `COPYABLE`, `WRAP_WITH_TRUSTED` |
| Token-assigned provenance | `LOCAL`, `KEY_GEN_MECHANISM`, `ALWAYS_SENSITIVE`, `NEVER_EXTRACTABLE`, `UNIQUE_ID`, `CRC64`, validation flags |
| Informational | `LABEL`, `SUBJECT`, dates |

**Role classification in full**, derived from the footnotes above (3.2):

| Role | Attributes | Why |
|---|---|---|
| **Intrinsic / material** (immutable, defines the object) | `CKA_CLASS`, `CKA_KEY_TYPE`, `CKA_CERTIFICATE_TYPE`, `CKA_EC_PARAMS`, `CKA_MODULUS`, `CKA_PUBLIC_EXPONENT`, `CKA_MODULUS_BITS`, `CKA_VALUE_LEN`, `CKA_PARAMETER_SET`, `CKA_VALUE` (secret/private: sensitive; public/cert/data: readable), `CKA_SEED` | footnotes 1,4,6 without 8 |
| **Mutable policy** (footnote 8) | `CKA_ENCRYPT`/`DECRYPT`/`SIGN`/`VERIFY`/`SIGN_RECOVER`/`VERIFY_RECOVER`/`WRAP`/`UNWRAP`/`DERIVE`/`ENCAPSULATE`/`DECAPSULATE` | footnote 8; gated by `CKA_MODIFIABLE` |
| **Set-once policy** (no footnote 8, may be set at creation) | `CKA_ALLOWED_MECHANISMS`, `CKA_WRAP_TEMPLATE`, `CKA_UNWRAP_TEMPLATE`, `CKA_DERIVE_TEMPLATE`, `CKA_ALWAYS_AUTHENTICATE`, `CKA_TOKEN`; `CKA_PRIVATE`, `CKA_MODIFIABLE`, `CKA_DESTROYABLE` (change only via copy) | |
| **One-way lifecycle** | `CKA_SENSITIVE` false→true; `CKA_WRAP_WITH_TRUSTED` false→true; `CKA_EXTRACTABLE` true→false; `CKA_COPYABLE` true→false; `CKA_TRUSTED` (SO-only true) | footnotes 11, 12, 10 |
| **Token-assigned provenance** (read-only) | `CKA_LOCAL`, `CKA_KEY_GEN_MECHANISM`, `CKA_ALWAYS_SENSITIVE`, `CKA_NEVER_EXTRACTABLE`, `CKA_UNIQUE_ID`, `CKA_PUBLIC_CRC64_VALUE` (generated keys), `CKA_OBJECT_VALIDATION_FLAGS`, `CKA_CHECK_VALUE` (derived, but deletable) | footnotes 2,4,6 / 13 |
| **Informational / locator** (mutable) | `CKA_LABEL` (all), `CKA_ID` (keys and X.509 certs), `CKA_START_DATE`/`END_DATE` (keys), `CKA_SUBJECT` (keys), `CKA_ISSUER`/`CKA_SERIAL_NUMBER` (certs), `CKA_APPLICATION`/`CKA_OBJECT_ID` (data; spec does not mark them modifiable) | |

**Two "only X is modifiable" statements must be read together.**

- §4.4 says only `CKA_LABEL` is modifiable among the *common storage* attributes.
- Key tables mark `CKA_ID`, the dates, `CKA_SUBJECT`, `CKA_DERIVE`, all usage bits, `CKA_SENSITIVE`, `CKA_EXTRACTABLE` and `CKA_PUBLIC_KEY_INFO` (private keys) with footnote 8.
- The effective mutable set on a key with `CKA_MODIFIABLE=true` is therefore {label, id, dates, subject, usage bits, one-way SENSITIVE/EXTRACTABLE, private-key PUBLIC_KEY_INFO}.

**`CKA_PUBLIC_KEY_INFO` on a private key is modifiable (footnote 8)**, and the spec makes the token responsible for verifying it. A non-conforming token turns it into a forgeable claim; see Q3 for SoftHSM.

**For EC, Edwards, ML-DSA, ML-KEM and SLH-DSA private keys, the spec gives no public-key attribute except the optional `CKA_PUBLIC_KEY_INFO`.** H1 in cakeys (an EC private identity read from a separate public object) is therefore a spec-level property. It is not only a SoftHSM quirk.

### Gaps

- **The 3.0 "Current Mechanisms" document was not downloaded.** Statements about when `CKA_EC_POINT`, `CKA_DERIVE_TEMPLATE` (absent from the 3.0 base text, present in 3.1 Table 29) or the Edwards key types were introduced are not verified per version.
- **The figure/table conversion dropped part of Table 14** (common object attributes; only `CKA_CLASS` rendered). It also truncated some names, e.g. `A_DERIVE_TEMPLATE` in Table 30. The content was cross-checked against the text.
- **The `CKA_ALLOWED_MECHANISMS` modifiability** is inferred from the absence of footnote 8. The spec text does not state it.

## Q2. Immutability, one-way attributes, token-set attributes, and provenance signals

### Takeaway

Spec-immutable attributes give a stable basis for "same object" checks:

- material (modulus, EC params, parameter set, cert `CKA_VALUE`);
- provenance flags (`LOCAL`, `KEY_GEN_MECHANISM`, `ALWAYS_SENSITIVE`, `NEVER_EXTRACTABLE`, `UNIQUE_ID`).

Usage bits, `CKA_ID` and `CKA_LABEL` are mutable whenever `CKA_MODIFIABLE=true`.

The provenance flags are only as trustworthy as the module that reports them. ykcs11 hard-codes `ALWAYS_SENSITIVE`/`NEVER_EXTRACTABLE`=TRUE. tpm2-pkcs11 keeps all attributes in a host-side SQLite store.

### Cited Findings

- **Modification is token-dependent:**
  - "attributes which Cryptoki specifies are modifiable may actually not be modifiable on some tokens";
  - modifiability "might depend on the values of certain attributes";
  - e.g. "CKA_SENSITIVE … can be changed from CK_FALSE to CK_TRUE, but not the other way around".

  Source: [3.2 §4.1.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).
- **Copying.** `C_CopyObject` creates a new object. It is refused with `CKR_ACTION_PROHIBITED` when `CKA_COPYABLE=false`. A copy of a `CKA_LOCAL=true` key is itself `CKA_LOCAL=true`. — [3.2 §4.1.3, Table 26](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **Provenance attributes are read-only and token-computed** (footnotes 2,4,6). `CKA_ALWAYS_SENSITIVE` means "has always had the CKA_SENSITIVE attribute set to CK_TRUE". `CKA_NEVER_EXTRACTABLE` means "has never had the CKA_EXTRACTABLE attribute set to CK_TRUE". — [3.2 Tables 29–30](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **Validation flags.** `CKA_OBJECT_VALIDATION_FLAGS` "can only be set in ways conforming to the module's validation". "Key objects typically take on the flags of the operation that created them". — [3.2 §4.15.3.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **`CKA_PUBLIC_CRC64_VALUE`** has footnotes 1,4,13:
  - The application MUST supply it on `C_CreateObject`.
  - It must not be supplied on generate.
  - The module generates it with `C_GenerateKeyPair`.

  Source: [3.2 Tables 27, 29, 38](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).
- **SoftHSM 2.7.0 flags private-key `CKA_PUBLIC_KEY_INFO` as modifiable (`ck8`)** and does not compute it: "TODO: CKA_PUBLIC_KEY_INFO is accepted, but we do not calculate it". `src/lib/SoftHSM.cpp` contains no reference to `CKA_PUBLIC_KEY_INFO`, so no correspondence check exists. On public-key objects the same attribute is `checks=0`. — [SoftHSM P11Objects.cpp](https://github.com/softhsm/SoftHSMv2/blob/2.7.0/src/lib/P11Objects.cpp) (`P11PublicKeyObj::init`, `P11PrivateKeyObj::init`); [P11Attributes.h](https://github.com/softhsm/SoftHSMv2/blob/2.7.0/src/lib/P11Attributes.h)
- **SoftHSM EC private keys** register only `CKA_EC_PARAMS` (`ck4|ck6`) and `CKA_VALUE` (`ck1|ck4|ck6|ck7`). — [SoftHSM P11Objects.cpp](https://github.com/softhsm/SoftHSMv2/blob/2.7.0/src/lib/P11Objects.cpp) (`P11ECPrivateKeyObj::init`)
- **SoftHSM KCVs** both match the spec's per-key-type definitions (§6.10.2, §6.8.2):
  - AES KCV is the ECB encryption of a single zero block.
  - Generic-secret KCV is computed from SHA-1 of the key data.

  Sources: [AESKey.cpp](https://github.com/softhsm/SoftHSMv2/blob/2.7.0/src/lib/crypto/AESKey.cpp), [SymmetricKey.cpp](https://github.com/softhsm/SoftHSMv2/blob/2.7.0/src/lib/crypto/SymmetricKey.cpp).
- **ykcs11 2.7.3 private-key getters:**

  | Attribute | Value |
  |---|---|
  | `CKA_SENSITIVE` | `CK_TRUE` ("Always true") |
  | `CKA_ALWAYS_SENSITIVE` | `CK_TRUE` ("Always true") |
  | `CKA_EXTRACTABLE` | `CK_FALSE` |
  | `CKA_NEVER_EXTRACTABLE` | `CK_TRUE` |
  | `CKA_COPYABLE` | `CK_FALSE` |
  | `CKA_MODIFIABLE` | `CK_FALSE` |
  | `CKA_DESTROYABLE` | `CK_TRUE` |
  | `CKA_LOCAL` | `is_local_key()`: true iff the slot's `origin == YKPIV_METADATA_ORIGIN_GENERATED` |
  | `CKA_ALWAYS_AUTHENTICATE` | true iff PIN policy is `YKPIV_PINPOLICY_ALWAYS` |
  | `CKA_ENCRYPT`, `CKA_WRAP`, `CKA_VERIFY` | false |
  | `CKA_SIGN`, `CKA_DECRYPT`, `CKA_UNWRAP`, `CKA_DERIVE` | from a static per-slot table |

  Source: [ykcs11/objects.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/objects.c).
- **ykcs11 origin and policies.** These come from an on-the-fly PIV attestation: success means GENERATED, and the PIN/touch policy is parsed from the attestation certificate. Otherwise they come from `ykpiv_get_metadata`. — [ykcs11/ykcs11.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/ykcs11.c) (~lines 995–1040)
- **tpm2-pkcs11 1.10.1:**
  - It adds `CKA_LOCAL=false` when missing, and `CKA_KEY_GEN_MECHANISM=CK_UNAVAILABLE_INFORMATION` on imported objects.
  - It rejects a template with "CKA_LOCAL cannot be true".
  - Object attributes are serialized into a text `attrs` column in its SQLite store.

  Sources: [src/lib/object.c](https://github.com/tpm2-software/tpm2-pkcs11/blob/1.10.1/src/lib/object.c) (~958–1006, 1157–1171), [src/lib/db.c](https://github.com/tpm2-software/tpm2-pkcs11/blob/1.10.1/src/lib/db.c) (~149–172, 764–772).
- **AWS CloudHSM Client SDK 5** marks `CKA_LOCAL`, `CKA_ALWAYS_SENSITIVE`, `CKA_NEVER_EXTRACTABLE` and `CKA_CHECK_VALUE` read-only (R) on generate/create/unwrap/derive. Its defaults on generation:
  - `CKA_PRIVATE`, `CKA_SENSITIVE` and `CKA_EXTRACTABLE` are True;
  - `CKA_SIGN` and `CKA_VERIFY` are True for AES/generic secret.

  Source: [AWS CloudHSM attribute tables](https://docs.aws.amazon.com/cloudhsm/latest/userguide/pkcs11-attributes-interpreting.html).

### Inferences

- **A change in any spec-immutable attribute between two observations means the object was replaced** (destroyed and recreated, or a different object now answers the locator). It does not mean the object was modified. This covers `LOCAL`, `KEY_GEN_MECHANISM`, `ALWAYS_SENSITIVE`, `NEVER_EXTRACTABLE`, `UNIQUE_ID`, `CRC64` and `CERTIFICATE_CATEGORY`. Recording them per realisation gives replace-in-place detection that does not depend on material.
- **The provenance flags are per object instance, not per material.** The same AES key can be `LOCAL=true` on the token that generated it and `LOCAL=false` after an unwrap onto another token. They belong in `realisations.<spec>.<token>`, not in `objects.<name>`.
- **One-way attributes give a meaningful "downgrade" notion:**
  - A spec with `CKA_SENSITIVE=true` and a live `ALWAYS_SENSITIVE=false` means the material was once exposable.
  - A spec with `EXTRACTABLE=false` and `NEVER_EXTRACTABLE=false` means it may have been wrapped out earlier.
  - cakeys cannot see either from the boolean spec alone.
- **Provenance flags are not uniformly trustworthy:**
  - ykcs11 reports `ALWAYS_SENSITIVE`/`NEVER_EXTRACTABLE`=TRUE for imported keys too (code reading). Only its `CKA_LOCAL` reflects origin, and that is backed by the device's attestation or metadata.
  - tpm2-pkcs11's flags are library bookkeeping in a host file. The TPM's own object attributes (`fixedTPM`, `sensitiveDataOrigin`), visible through TPM2_Certify, are ground truth. The PKCS#11 attributes are not.
  - A lock should record these flags as *observed provenance with module attribution*, not as proof.
- **On SoftHSM, `CKA_PUBLIC_KEY_INFO` on a private key is an unverified claim (code reading; not reproduced).** Two paths exist:
  - **Import (the main path).** Nothing forbids supplying it on `C_CreateObject` (no `ck2`). A replacement private key can therefore be *imported* with a forged SPKI, even with `CKA_MODIFIABLE=false`.
  - **Later edit.** A logged-in user can also set it via `C_SetAttributeValue` when `CKA_MODIFIABLE=true` (`ck8`).

  cakeys `public_spki()` reads `CKA_PUBLIC_KEY_INFO` *first* (`crates/pkcs11/src/token.rs` `public_spki`). That affects RSA private keys too, even though their `CKA_MODULUS` is immutable. This widens H1 beyond "EC/Edwards on SoftHSM".

### Gaps

- **It was not tested whether any module verifies an application-supplied `CKA_PUBLIC_CRC64_VALUE` on `C_CreateObject`.** Footnote 1 makes the application supply it. If modules accept it unverified, it binds only generated keys.
- **The behaviour of nShield, Luna and Utimaco for `ALWAYS_SENSITIVE`/`NEVER_EXTRACTABLE`/`LOCAL` after unwrap or import was not researched.**
- **Whether ykcs11's metadata path reports origin IMPORTED for imported keys on firmware ≥5.3** was not verified against hardware. Code reading suggests it does.

## Q3. Is `CKA_UNIQUE_ID` a usable stable identifier? How real tokens populate key attributes

### Takeaway

`CKA_UNIQUE_ID` (since 3.0) is token-generated and read-only. It is only guaranteed unique among objects visible to a session, and it MAY be reused after `C_InitToken`. It is an instance handle, not a content identity.

Among open-source modules, only kryoptic populates it (random UUIDv4). SoftHSM 2.7.0, tpm2-pkcs11, ykcs11 and OpenSC define it but do not implement it. Securosys Primus does not support it. CloudHSM does not list it, and Luna uses a vendor `CKA_OUID` instead.

It is at most an optional, per-realisation replace-in-place tripwire.

### Cited Findings

- **Spec semantics:**
  - "Any time a new object is created, a value for CKA_UNIQUE_ID MUST be generated by the token."
  - Values "MUST be unique across all objects visible to any particular session, and SHOULD be unique across all objects created by the token. Reinitializing the token, such as by calling C_InitToken, MAY cause reuse."
  - Specifying or modifying it "MUST fail" with `CKR_ATTRIBUTE_READ_ONLY`.

  Source: [3.2 §4.4.1](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html). The same text is in [3.0 base](https://docs.oasis-open.org/pkcs11/pkcs11-base/v3.0/os/pkcs11-base-v3.0-os.html).
- **kryoptic 1.5.3:**
  - `generate_unique()` assigns `Uuid::new_v4()` at creation or import.
  - `generate_stable_unique()` builds a deterministic UUIDv8 from "kryoptic" + class + id, only for built-in profile and mechanism objects.
  - Copying "regenerates the unique id".
  - The SQLite storage looks objects up by `CKA_UNIQUE_ID`.

  Sources: [src/object/mod.rs](https://github.com/latchset/kryoptic/blob/v1.5.3/src/object/mod.rs) (~127–165), [src/token.rs](https://github.com/latchset/kryoptic/blob/v1.5.3/src/token.rs) (~940–960), [src/storage/sqlite.rs](https://github.com/latchset/kryoptic/blob/v1.5.3/src/storage/sqlite.rs).
- **kryoptic copies the computed `CKA_PUBLIC_KEY_INFO` onto the private key** for RSA and EdDSA keys it generates. — [src/rsa.rs](https://github.com/latchset/kryoptic/blob/v1.5.3/src/rsa.rs) (~720), [src/ec/eddsa.rs](https://github.com/latchset/kryoptic/blob/v1.5.3/src/ec/eddsa.rs) (~418)
- **Modules that do not implement `CKA_UNIQUE_ID`:**
  - **SoftHSM 2.7.0:** it appears only as a `#define` in `src/lib/pkcs11/pkcs11.h`, with no handling in the object code. `CKA_PUBLIC_KEY_INFO` is accepted but not computed. — [SoftHSM](https://github.com/softhsm/SoftHSMv2/tree/2.7.0/src/lib)
  - **tpm2-pkcs11 1.10.1:** no reference to `CKA_UNIQUE_ID` in `src/`. — [tpm2-pkcs11](https://github.com/tpm2-software/tpm2-pkcs11/tree/1.10.1/src)
  - **ykcs11 2.7.3:** only the header `#define` in `ykcs11/pkcs11t.h`. — [ykcs11](https://github.com/Yubico/yubico-piv-tool/tree/yubico-piv-tool-2.7.3/ykcs11)
  - **OpenSC 0.27.1:** appears in `pkcs11-display.c`'s printing table, not in object construction. — [OpenSC src/pkcs11](https://github.com/OpenSC/OpenSC/tree/0.27.1/src/pkcs11)
  - **pkcs11-provider 1.3.0:** defines it but never reads it. — [pkcs11-provider src](https://github.com/openssl-projects/pkcs11-provider/tree/v1.3.0/src)
- **ykcs11's public key for a PIV slot is chosen at session open (`C_OpenSession`), in this precedence:**
  1. An on-the-fly attestation. On success the slot is marked origin GENERATED.
  2. Otherwise `ykpiv_get_metadata`, using its public key if one is present.
  3. Otherwise `store_cert(..., CK_FALSE)`, from the certificate in the slot's data object. The source comment says it "Will only overwrite key if not set from attestation or metadata".

  When both attestation and metadata fail, ykcs11 "fall[s] back to assuming we have keys for cert objects". It adds private and public key objects for the slot on the strength of the certificate alone. The private-key object's `CKA_EC_POINT`/`CKA_MODULUS` are served from that same `pkeys` entry. — [ykcs11/ykcs11.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/ykcs11.c) (~995–1040, 1631), [ykcs11/objects.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/objects.c) (`store_cert`, `CKA_EC_POINT` getter)
- **Securosys Primus:**
  - `CKA_UNIQUE_ID` is "Not supported by the Primus PKCS#11 provider".
  - Primus requires labels "unique for a given 'category'".
  - It appends a hidden suffix `label@?!<uid>` to duplicates unless `unique_label=true` (provider 2.7.0+).
  - It falls back to hex(`CKA_ID`) as the label.

  Source: [Securosys: Identifiers and Labels in PKCS#11](https://docs.securosys.com/pkcs/Concepts/identifiers).
- **AWS CloudHSM Client SDK 5:**
  - The attribute tables do not list `CKA_UNIQUE_ID`.
  - EC private keys: `CKA_EC_POINT` ✖ on `GetAttributeValue`, and `CKA_PUBLIC_KEY_INFO` is not listed.
  - `CKA_CHECK_VALUE` is readable for EC/RSA/AES/DES3 but ✖ for generic secret.
  - ML-DSA is supported with a vendor `CKA_CLOUDHSM_PARAMETER_SET`, and "ML-DSA key import through C_CreateObject is not supported".

  Source: [AWS CloudHSM attribute tables](https://docs.aws.amazon.com/cloudhsm/latest/userguide/pkcs11-attributes-interpreting.html).
- **Thales Luna (from a search-engine summary only, not read in full):** Luna exposes a vendor attribute `CKA_OUID`, a 12-byte identifier "unique across all Luna HSMs". `CA_GetObjectUID`/`CA_GetObjectHandle` map between OUID and handle. — [Thales Luna attribute defaults](https://thalesdocs.com/gphsm/luna/7/docs/pci/Content/sdk/design/attribute_defaults.htm), [Luna extensions](https://thalesdocs.com/gphsm/luna/7.7.0/docs/network/Content/sdk/extensions/safenet_extensions.htm)
- **p11-kit RPC 0.26.5** has typed serializers for array attributes (`CKA_WRAP_TEMPLATE`, `CKA_DERIVE_TEMPLATE`, `CKA_ALLOWED_MECHANISMS`) and a default branch for other attribute types, so unknown attributes are still forwarded. — [p11-kit/rpc-message.c](https://github.com/p11-glue/p11-kit/blob/0.26.5/p11-kit/rpc-message.c) (`map_attribute_to_value_type`, ~796–880)

### Inferences

- **`CKA_UNIQUE_ID` cannot serve as a CA-ID or a lock identity:**
  - it is random (kryoptic);
  - it changes on copy, import or backup-restore to another token;
  - it may be reused after re-initialisation;
  - it is absent on the modules cakeys supports today (SoftHSM, tpm2-pkcs11, ykcs11, p11-kit→SoftHSM).

  Its only role would be an optional `uniqueId` pin in a realisation. When the module provides it, a different value under the same locator with the same CA-ID means "same material, new object instance". That could be a note, or under a strict mode an error, and would flag e.g. a delete-and-reimport that reset policy bits.
- **H1 is wider than SoftHSM.** By spec, EC/Edwards/PQ private objects carry no public point. CloudHSM's EC private key exposes neither `CKA_EC_POINT` nor `CKA_PUBLIC_KEY_INFO`, so on CloudHSM too cakeys' private-key `pubkeyhash` would come from the unbound public object. kryoptic avoids it for the keys it generates.
- **On ykcs11 the private key's "own" public point may not be bound either.** It is bound when it comes from attestation (signed by the device attestation key) or from device metadata (reported by the card). In the certificate fallback (firmware without metadata, e.g. before YubiKey 5.3), it is derived from a certificate anyone with the PIV management key can overwrite. The key objects are then synthesised on the assumption that a key exists (inference from code reading).
- **The YubiKey example lock** (`examples/yubikey-secureboot.toml`: imported Secure Boot keys, `publicOnly`) is affected by this:
  - Imported keys cannot be attested, so their `pubkeyhash` comes from metadata on metadata-capable firmware, else from the slot certificate.
  - The lock records `token.firmware`, which tells which path applied. Recording the path itself would be better.

### Gaps

- **nShield (Entrust) behaviour was not researched:** `CKA_UNIQUE_ID`, `CKA_PUBLIC_KEY_INFO` on private keys, `CKA_LOCAL` on imported keys. The same holds for Luna beyond the search summary, and for Utimaco.
- **Whether CloudHSM populates `CKA_PUBLIC_KEY_INFO` at all** is not stated in its tables.
- **OpenSC's PKCS#15 framework** (smart cards via `opensc-pkcs11.so`) was not traced for which key attributes it synthesises. It is known to synthesise most attributes from PKCS#15 metadata, but that was not verified here.

## Q4. RFC 7512 URIs: which components identify an object; how consumers select objects; "pure locator" implications

### Takeaway

RFC 7512 object identification uses only `object` (`CKA_LABEL`), `id` (`CKA_ID`) and `type` (class). Token, slot and library components narrow the search space. Query attributes (`pin-source`, `pin-value`, `module-name`, `module-path`) are explicitly *not* identity.

Missing attributes act as wildcards, and real consumers bind keys by `CKA_ID` (OpenSSH), not by label. A cakeys URI that verified one object can therefore select a different object in a consumer unless it carries every locator attribute cakeys used, plus `type`. Adding a token-assigned `serial` would also help.

### Cited Findings

- **Path attributes** — [RFC 7512 §2.3](https://datatracker.ietf.org/doc/html/rfc7512):
  - token: `token`, `manufacturer`, `serial`, `model`;
  - library: `library-manufacturer`, `library-description`, `library-version`;
  - storage object: `object`, `id`, `type` (`public` / `private` / `cert` / `secret-key` / `data`);
  - slot: `slot-manufacturer`, `slot-description`, `slot-id`.

  Query attributes are `pin-source`, `pin-value`, `module-name` and `module-path`.
- **Scope.** "The set of attributes describing a storage object can contain an object label, its type, and its ID." "A PKCS #11 URI cannot identify other objects … aside from storage objects", e.g. hardware features or mechanisms. — [RFC 7512 §1](https://datatracker.ietf.org/doc/html/rfc7512)
- **Encoding and duplicates.** Each path attribute appears at most once. The `id` value "SHOULD be entirely percent-encoded" because `CKA_ID` is binary. — [RFC 7512 §2.3](https://datatracker.ietf.org/doc/html/rfc7512)
- **Module attributes:**
  - `module-name` is a case-insensitive name without affixes;
  - `module-path` is an absolute path, and a relative one "SHOULD be rejected";
  - consumers "MAY refuse to accept either";
  - if present, "only those modules found matching … SHOULD be used";
  - using both "SHOULD be avoided".

  Source: [RFC 7512 §2.3](https://datatracker.ietf.org/doc/html/rfc7512).
- **Matching.** A URI may identify objects, tokens, slots or libraries, depending on context. "a URI with only library attributes may either represent all objects in all tokens in all Cryptoki libraries identified by the URI, all tokens in those libraries, or just the libraries". — [RFC 7512 §2.5](https://datatracker.ietf.org/doc/html/rfc7512)
- **`C_FindObjectsInit`:**
  - "The matching criterion is an exact byte-for-byte match with all attributes in the template."
  - "The object search operation will only find objects that the session can view. For example, an object search in an 'R/W Public Session' will not find any private objects."

  Source: [3.2 §5.7.7](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html).
- **pkcs11-provider 1.3.0:**
  - Its URI parser recognises all RFC 7512 path attributes (`library-*`, `token`, `manufacturer`, `model`, `serial`, `slot-*`, `id`, `object`, `type`) and the `pin-value`/`pin-source` query attributes.
  - `module-name`/`module-path` handling was not found in `util.c`; the module comes from provider configuration.
  - When it emits a URI for an object, it uses `CKA_ID` and `CKA_LABEL` plus the class-derived `type`.

  Source: [src/util.c](https://github.com/openssl-projects/pkcs11-provider/blob/v1.3.0/src/util.c) (~114–126, 558–577, 710–735).
- **OpenSSH 10.6p1 `ssh-pkcs11.c`:**
  - It enumerates `CKO_CERTIFICATE` and `CKO_PUBLIC_KEY` objects.
  - To sign, it finds the private key with template {`CKA_CLASS=CKO_PRIVATE_KEY`, `CKA_ID=<keyid>`, `CKA_SIGN=true`}, retrying without `CKA_SIGN`, and takes the first match.
  - It honours `CKA_ALWAYS_AUTHENTICATE`.
  - Keys it generates get the same `CKA_ID` and `CKA_LABEL` on the public and private halves.

  Source: [openssh-portable ssh-pkcs11.c](https://github.com/openssh/openssh-portable/blob/master/ssh-pkcs11.c) (10.6p1 tarball, ~lines 340–383, 1661–1683).
- **sbsigntools 0.9.5** loads keys through the OpenSSL ENGINE API (`fileio_read_engine_key` → `ENGINE_by_id(engine)`). Object selection is delegated to the engine, typically libp11's `pkcs11` engine, with the key argument as a PKCS#11 URI. — [sbsigntools src/fileio.c](https://git.kernel.org/pub/scm/linux/kernel/git/jejb/sbsigntools.git/tree/src/fileio.c?h=v0.9.5) (~42–90)
- **cakeys' URI** contains `token=<tokenLabel>`, plus `object=` and/or `id=` for whichever locator fields are set, plus `type=`. It has no `module-path`, "A pure locator". — `crates/pkcs11/src/token.rs` `uri()`; `docs/DESIGN.md` §4.2
- **The cakeys YubiKey example** locates the private keys by `CKA_ID` and the certificates by `CKA_LABEL`, because "CKA_ID 05 is shared with the slot's attestation certificate". — `examples/yubikey-secureboot.toml`

### Inferences

- **Locator divergence.** cakeys proves "exactly one object of class C matches {label, id}" on the token it opened. A consumer receiving the URI applies the same template, so as long as the URI includes `type` and every locator field, they agree on the *same token*. Two caveats follow.
  - **Token selection.** `token=` is the user-settable token label (`C_InitToken`), which is not guaranteed unique across modules or slots. `serial=` comes from `C_GetTokenInfo`, is token-assigned, and is already recorded in the lock (`realisations.*.token.serial`). Adding `serial=` (and possibly `model=`/`manufacturer=`) to the emitted URI keeps it a pure locator while narrowing it to the device the lock describes.
  - **Login state.** `Token::open` logs in whenever a PIN source is configured, regardless of `publicOnly`. When no PIN is configured, as in the YubiKey example, cakeys' ambiguity check runs in a public session, so `CKA_PRIVATE=true` objects are invisible (§5.7.7). A logged-in consumer may then see two matches under the same locator (e.g., a second private key with the same `CKA_ID`) where cakeys saw one. The lock should record that the uniqueness check was done in a public session.
- **The private key behind the pubkeyhash may not be the one a consumer signs with.** Consumers that pair by `CKA_ID` (OpenSSH; libp11-style engines in general) select "the private key with this `CKA_ID`". cakeys verifies identity via the public half or certificate, which share the `CKA_ID` only by convention ("Cryptoki does not enforce these associations", [3.2 §4.8.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)). Unless binding is proven by proof-of-possession, the consumer may sign with a different private key than the one whose `pubkeyhash` the lock records. This is H1 seen from the consumer side.
- **`module-path` belongs out of the URI.** Leaving it out is consistent with RFC 7512's own preference for `module-name` and its security caveat. Provenance of the module is better recorded in the lock, as cakeys does.

### Gaps

- **GnuTLS/p11tool selection rules were not traced in source:** `gnutls_pkcs11_privkey_import_url` and whether it pairs by `CKA_ID`. Neither were libp11 engine matching for sbsigntools, nor systemd-cryptenroll/cryptsetup token plugins, which store a PKCS#11 URI in the LUKS2 token and use the matched certificate's public key with the private key found by the URI.
- **OpenSC `pkcs11-tool`'s selection rules were not traced:** `--id`/`--label`/`--type` filters, and whether it requires uniqueness or takes the first match.
- **Whether upstream OpenSSH (as opposed to distribution patches) accepts RFC 7512 URIs** in `PKCS11Provider`/`ssh-add -s` was not confirmed in this pass.
- **No RFC 7512 successor or registered attribute for `CKA_UNIQUE_ID`** was found. This was not exhaustively searched.

## Q5. Typical usage patterns: generation templates, cert+key pairing by CKA_ID, PIV fixed slots, sessions/login, C_SetAttributeValue

### Takeaway

Real deployments rely on four conventions:

- the *public* template carries the domain (EC params, modulus bits, parameter set);
- the private template carries policy;
- the key pair and certificate are linked only by an equal `CKA_ID`, by convention;
- PIV tokens have fixed objects with fixed `CKA_ID`/label and immutable policy.

Visibility depends on login, and every mutable attribute can be changed by anyone holding the user PIN unless `CKA_MODIFIABLE=false`.

### Cited Findings

- **Generation templates:**
  - "when generating an EC private key, the EC domain parameters are not specified in the key's template … [they] are specified in the template for the EC public key". — [3.2 §6.3.4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
  - The same holds for the ML-DSA parameter set. — [3.2 §6.67.3](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
  - "all the required attributes … that do not have default values MUST be specified … either in the template or by the function itself". — [3.2 §4.1](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **Pairing by `CKA_ID`:**
  - "the key identifier for a public key and its corresponding private key should be the same. The key identifier should also be the same as for the corresponding certificate … Cryptoki does not enforce these associations". — [3.2 §4.8.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
  - "It is intended that the CKA_ID value be identical to the key identifier in such a certificate extension, although this will not be enforced". — [3.2 §4.6.3](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **The private key should yield its public key.** "private keys of any type SHOULD store sufficient information to retrieve the public key information", which is why `CKA_PUBLIC_EXPONENT` became mandatory for RSA in 2.40. — [3.2 §4.10](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **PIV fixed slots in ykcs11 2.7.3.** Objects are static entries in `piv_objects[]` with fixed labels and a `sub_id` that is the `CKA_ID` byte:
  - "X.509 Certificate for PIV Authentication" → 1;
  - "Card Authentication" → 4;
  - "Retired Key 1" → 5 … "Retired Key 14" → 18.

  Attestation certificates share the slot's `sub_id`. — [ykcs11/objects.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/objects.c) (~59–72; `ykcs11.h` `certs[26]`, `atst[26]`)
- **ykcs11 objects report `CKA_MODIFIABLE=false` and `CKA_COPYABLE=false`.** — [ykcs11/objects.c](https://github.com/Yubico/yubico-piv-tool/blob/yubico-piv-tool-2.7.3/ykcs11/objects.c)
- **Per-use authentication.** `CKA_ALWAYS_AUTHENTICATE=true` requires `C_Login(CKU_CONTEXT_SPECIFIC)` after each `C_SignInit`/`C_DecryptInit`. Failing to do so returns `CKR_USER_NOT_LOGGED_IN`, and "repeated failed re-authentication attempts may cause the PIN to be locked". — [3.2 §4.10](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **Private objects need login.** "When the CKA_PRIVATE attribute is CK_TRUE, a user may not access the object until the user has been authenticated to the token." — [3.2 §4.4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **`C_SetAttributeValue`.** All the create-time error rules apply except template incompleteness. — [3.2 §4.1.2, §5.7.6](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **What cakeys creates:**
  - **Private template:** `CKA_TOKEN=true`, the locator attributes and the spec's booleans.
  - **Public template:** `CKA_TOKEN`, the locator, `CKA_MODULUS_BITS`+`CKA_PUBLIC_EXPONENT=65537` or `CKA_EC_PARAMS`, `CKA_VERIFY=true` and `CKA_PRIVATE=false`.
  - **Secret keys:** `CKA_VALUE_LEN` and the policy booleans, via `CKM_AES_KEY_GEN` or `CKM_GENERIC_SECRET_KEY_GEN`.

  Source: `crates/pkcs11/src/token.rs` `create()`.
- **cakeys spec booleans** are limited to SIGN, VERIFY, ENCRYPT, DECRYPT, WRAP, UNWRAP, DERIVE, SENSITIVE, EXTRACTABLE, MODIFIABLE and PRIVATE. — `crates/pkcs11/src/token.rs` `bool_attr()`; `docs/DESIGN.md` §4.1

### Inferences

- **The generated public half's attributes are fixed by cakeys code, not by the spec.** These are `VERIFY=true`, `PRIVATE=false` and the public exponent. They are not part of the spec digest and are never checked on verify. A public object whose `CKA_VERIFY`/`CKA_ENCRYPT`/`CKA_WRAP`/`CKA_TRUSTED`/`CKA_WRAP_TEMPLATE` was later changed would go unnoticed.
- **PIV tokens make policy immutable and partly implicit.** PIN and touch policy are not PKCS#11 attributes, except `ALWAYS_AUTHENTICATE` for PIN-always. Touch policy is invisible in PKCS#11 and observable only via attestation or metadata. For "config+lock completely describes state", the YubiKey's PIN/touch policy has to come from the attestation certificate (Q6).

### Gaps

- **Typical HSM vendor generation-template conventions were not surveyed.** These include `CKA_ALLOWED_MECHANISMS` use, and wrap/unwrap templates for key escrow (e.g., the CloudHSM trusted-wrapping workflow).

## Q6. Gap analysis: what cakeys records, checks, ignores or cannot observe; what config+lock need to "completely describe" an object

### Takeaway

cakeys pins material (CA-IDs), intrinsic type, a declared subset of eleven boolean policy attributes, locator/URI and module provenance, but not the object's full observed policy, its provenance flags, non-boolean policy, certificate or public-half policy, or a cryptographic private↔public binding (H1, widened by SoftHSM's unverified `CKA_PUBLIC_KEY_INFO`). Non-extractable secret values and PIV PIN/touch policy are unobservable through PKCS#11 and need commitments or attestation.

### Cited Findings

**What cakeys records, checks and ignores** (code reading of the cakeys repo)

**Spec facts that bear on completeness**

- **Defaults are token-specific (footnote 9):**
  - `CKA_PRIVATE`'s default is "token-specific, and may depend on the values of other attributes" ([3.2 §4.4](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)).
  - CloudHSM defaults `CKA_SIGN`/`CKA_VERIFY` to True for generated AES/generic secret keys, and `CKA_EXTRACTABLE` to True ([AWS](https://docs.aws.amazon.com/cloudhsm/latest/userguide/pkcs11-attributes-interpreting.html)).
- **Sensitive values cannot be read.** Attributes with footnote 7 (`CKA_VALUE`, private exponents, `CKA_SEED`) "Cannot be revealed if object has its CKA_SENSITIVE attribute set to CK_TRUE or its CKA_EXTRACTABLE attribute set to CK_FALSE". — [3.2 Table 13](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **The private key must carry the public key when it is supplied.** If `CKA_PUBLIC_KEY_INFO` is supplied on create, copy or set, "the token MUST verify correspondence … by deriving a public key … or by doing a sign and verify operation". — [3.2 §4.10](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html)
- **The KCV is weak:** 3 bytes, "Non-uniqueness", optional ("if supported"), suppressible at creation and destroyable via `C_SetAttributeValue`. Its algorithm is fixed per key type by the spec: AES = ECB of a zero block; generic secret and ChaCha20 = SHA-1 of the value. CloudHSM does not offer it for generic secrets. — [3.2 §4.11, §6.8.2, §6.10.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/pkcs11-spec-v3.2-os.html); [AWS](https://docs.aws.amazon.com/cloudhsm/latest/userguide/pkcs11-attributes-interpreting.html)
- **The review's open items** (H1, M1 read-write sessions, D5 unwrap-only AES has no deterministic identity) are listed in `docs/REVIEW-2026-11-11.md`.

### Inferences

These are the recommendations for the config/lock schema.

**1. Make policy closed-world.** "Completely describes" fails today. An undeclared attribute takes a token-specific default (footnote 9; CloudHSM defaults AES `CKA_SIGN=true`) and is never read. Two options:

- (a) **Validate that a spec declares every policy attribute applicable to its class.** Per class this is all footnote-8 usage bits plus SENSITIVE, EXTRACTABLE, PRIVATE, MODIFIABLE, COPYABLE, DESTROYABLE, ALWAYS_AUTHENTICATE (private), WRAP_WITH_TRUSTED and TRUSTED.
- (b) **Record in each realisation the full observed policy vector** (`policy = { CKA_SIGN = true, … }`, every applicable boolean the module answers) and compare it on verify. Drift in an undeclared attribute becomes a conflict or a warning.

(b) is backwards-compatible with existing specs and also captures module defaults. (a) is what a "declarative" config would demand. A combination is possible: a spec may stay partial, and the lock pins the rest.

**2. Extend the spec's value type beyond `bool`:**

   | Attribute(s) | Proposed type |
   |---|---|
   | `CKA_ALLOWED_MECHANISMS` | list of `CKM_*` |
   | `CKA_WRAP_TEMPLATE`/`UNWRAP_TEMPLATE`/`DERIVE_TEMPLATE` | nested attribute maps |
   | `CKA_START_DATE`/`END_DATE` | dates |
   | `CKA_SUBJECT` | DER |

   Add the missing booleans too: COPYABLE, DESTROYABLE, ALWAYS_AUTHENTICATE, WRAP_WITH_TRUSTED, SIGN_RECOVER, VERIFY_RECOVER, ENCAPSULATE, DECAPSULATE, TOKEN. This changes the spec-digest JSON, so a frozen-identifier v2 is needed (`docs/DESIGN.md` §10).

**3. Record provenance flags per realisation, compared as immutable:** `local`, `keyGenMechanism`, `alwaysSensitive`, `neverExtractable`, `objectValidationFlags` (3.2), `publicCrc64` (3.2), `uniqueId` (when present), and the cert's `certificateCategory`/`trusted`.

- They are spec read-only, so any change between realise and verify means the object instance was replaced. That justifies at least a warning, and a policy-configurable error.
- Do not put them in `objects.<n>`: the same material legitimately differs per token (generated vs unwrapped).
- Attribute them to the module, because ykcs11 hard-codes two of them and tpm2-pkcs11 stores them in a host file.
- Optionally let the spec *require* provenance, e.g. `requireLocal = true` or `requireNeverExtractable = true`, which is the declarative counterpart.

**4. Fix the public-key source order (H1 and its widening):**

- Derive the SPKI from spec-immutable components when they exist: RSA `CKA_MODULUS`+`CKA_PUBLIC_EXPONENT` (footnotes 1,4,6) and `CKA_EC_POINT` on public objects.
- Use private-key `CKA_PUBLIC_KEY_INFO` only as a cross-check that must agree. On SoftHSM it is `ck8` and unverified.
- Where the private object has no public material (EC/Edwards/PQ by spec; SoftHSM, CloudHSM), bind via proof-of-possession, as REVIEW H1 proposes. That means sign a fresh challenge, ECDH or KEM-decapsulate, or RSA-decrypt.
- Record the binding method in the realisation, e.g. `binding = "self" | "pop-sign" | "pop-ecdh" | "unbound"`. Treat `unbound` like `publicOnly`: an explicit, recorded opt-in.
- The 3.2 `CKA_PUBLIC_CRC64_VALUE` on a *generated* private key could serve as a cheap consistency check between private and public objects on honest 3.2 tokens. It is a non-cryptographic CRC and is application-supplied on import, so it is not a security binding.

**5. Declare cert/key pairing explicitly.** Consumers pair by `CKA_ID` (OpenSSH), so a spec or lock relation is useful, e.g. `pairs = ["whonix-db-cert"]`. cakeys would then assert that every object of the paired classes under the consumer-visible `CKA_ID` has the same `pubkeyhash`, and that the private key proves possession. Today the lock contains equal `pubkeyhash` values for `whonix-db` and `whonix-db-cert`, but no check ties them together.

**6. Cover the policy cakeys cannot yet express:**

- **Certificates.** Policy attributes on certificate specs are refused today (`ops.rs`). So a certificate's `CKA_PRIVATE`/`CKA_MODIFIABLE`/`CKA_TRUSTED`/`CKA_CERTIFICATE_CATEGORY` are neither declared nor recorded. The mutable `CKA_ID`/`CKA_ISSUER`/`CKA_SERIAL_NUMBER` are not recorded either. Allowing a certificate-specific attribute set, or recording the observed values per realisation, would close this.
- **The public half of a key pair.** Read its policy when the spec covers a key pair: `CKA_VERIFY`/`ENCRYPT`/`WRAP`/`TRUSTED`/`WRAP_TEMPLATE` and `CKA_MODIFIABLE`.

**7. Use commitments or attestation for what is unobservable:**

- **Non-extractable secret values.** cakeys' commitment schemes cover these already. Standard `CKA_CHECK_VALUE` is at most a weak corroborator or an opt-in fallback for D5 unwrap-only AES keys, and must not be identity:
  - it is 24-bit, optional and deletable;
  - its algorithm is fixed per key type by the spec (AES = ECB zero block; generic secret = SHA-1 of the value).

  If used, it would be a new scheme name per key type (e.g. `kcv-std`).
- **PIV PIN/touch policy and "generated on device".** Not expressible in PKCS#11 except `ALWAYS_AUTHENTICATE`. The YubiKey attestation certificate, under the device attestation key in slot f9 and chained to the Yubico root, covers them. Record its hash and parsed policy per realisation (`attestation = { kind = "piv", sha256 = …, pinPolicy, touchPolicy, origin }`).
- **TPM-backed keys.** Use TPM2_Certify of the object's attributes (`fixedTPM`, `sensitiveDataOrigin`) instead of tpm2-pkcs11's host-side PKCS#11 attributes.
- **HSMs.** Use vendor key attestation where available (not researched; Gap).

**8. Record the instance identifier when it exists.** Store `CKA_UNIQUE_ID` (or a vendor equivalent such as Luna `CKA_OUID`, if confirmed readable) per realisation as an instance pin. It must never be a CA-ID: it is random, per token and reusable after `C_InitToken`. Only kryoptic populates it among cakeys-relevant modules.

**9. Locator and URI:**

- Emit `serial=` (token-assigned, already in the lock) alongside `token=` in the URI.
- Ensure `type` and every locator field are always present.
- Note in the lock whether the uniqueness check ran in a public or a user session. A public session hides `CKA_PRIVATE=true` duplicates (§5.7.7), which matters for `publicOnly`.
- Consider checking, when logged in, that no *other* class sharing the `CKA_ID` (e.g. a second private key) exists, since consumers resolve by `CKA_ID`.

**10. PQ readiness.** Add `parameterSet` (`CKP_ML_DSA_44/65/87`, `CKP_ML_KEM_*`, `CKP_SLH_DSA_*`) to `ObjectCfg` and `objects.<n>.type`. The public value is raw `CKA_VALUE` (FIPS 204/203/205 encodings), not SPKI. A `pubkeyhash` for PQ keys must fix an SPKI wrapping (algorithm OIDs, parameter-set mapping) as a new, frozen scheme definition, or define a new scheme over the raw value plus parameter set. Expect vendor deviations: CloudHSM uses `CKA_CLOUDHSM_PARAMETER_SET`, and ML-DSA import is not supported there.

**11. Summary: where each attribute belongs**

| Where | Contents | Treatment |
|---|---|---|
| Config `objects` | intrinsic type, including parameter set | |
| Config `specs` | full policy (closed-world), typed values, optional provenance requirements, pairing | |
| Lock `objects` | CA-IDs, type, commitment label | identity |
| Lock `realisations` | spec digest, observed policy vector, provenance flags, binding method, unique ID, attestation digest, session kind, URI, module/token | compare: policy and immutables; warn: module/token/provider |
| Unobservable | sensitive values, PIV PIN/touch policy, TPM origin, HSM key origin | commitments and attestations only |

### Gaps

- **Vendor key-attestation formats were not researched:** CloudHSM key attestation, Luna, nShield (Security World/KeySafe certificates), Utimaco. This blocks a concrete "attestation" schema beyond YubiKey PIV and TPM2.
- **How tokens behave when a spec asks for `CKA_SENSITIVE=false` on a private key is untested,** i.e. whether `ALWAYS_SENSITIVE` is then false. The same holds for whether SoftHSM enforces the one-way rules on `C_SetAttributeValue`.
- **The IETF LAMPS SPKI encodings for ML-DSA, ML-KEM and SLH-DSA** (RFC numbers and final OIDs) were not checked in this pass. They are needed before freezing a PQ `pubkeyhash` scheme.
- **Whether p11-kit's RPC (0.26.5) forwards `CKA_PUBLIC_CRC64_VALUE`, `CKA_OBJECT_VALIDATION_FLAGS` and `CKA_PARAMETER_SET` with correct `CK_ULONG` typing** was not verified. They fall to the default serializer branch.
