# Review: crates/cli/tests/object_matrix/mod.rs (830 lines)

Reviewed 2026-11-18 [read]. Summary: a fixed grid of about 1,500 objects (generated and imported
keys, imported private keys by where their public half is, certificates, data objects) is created
on a token through cryptoki. Each is declared as it is and realised, and the whole outcome table
(mode, schemes, binding, or exit code) is compared byte for byte with
`spec-coverage/objects/<token>.toml`. This is the strongest guard in the suite against "clean tests
decide what keys we support". It pins exit codes and modes, never prose. The cost is resource use
and a regenerate switch.

## Findings

### F1. Up to 8 parallel `cakeys` processes on one token; any contention flake fails the whole table — risk

**Verification:** withdrawn (speculative; each named mechanism is guarded). The test's own session is dropped when the creation block ends (object_matrix/mod.rs:739-750), before any worker starts; tpm2 runs 4 workers, not 8 (tpm2.rs:852-853), behind abrmd's serialisation; kryoptic reaches SQLite through rusqlite, whose connections carry a default 5 s busy timeout (`sqlite3_busy_timeout` and rusqlite's busy.rs are in libkryoptic_pkcs11.so 1.5.4), so a concurrent write waits rather than returning SQLITE_BUSY; SoftHSM's file object store locks per object for multi-process use. No flake is on record (ISSUES.md:45, nextest 524/524). [read]
`object_matrix/mod.rs:754-770` with `reference/matrix.rs:22` and `tpm2.rs` (8 workers). Each worker
runs a `cakeys` process per row against the same token store while the test's own session holds
another. A transient refusal under contention (SoftHSM's file lock, kryoptic's sqlite busy,
tpm2-pkcs11's store) changes one row's exit, and the byte comparison fails with the whole table.
Unverified from reading: whether any reference module returns `CKR_DEVICE_ERROR`/`SQLITE_BUSY`
under this load. If a flake appears, `report.txt` shows the row. A retry of only the rows whose exit
is 16 (unavailable) would separate contention from a real change. [read]

### F2. `CAKEYS_UPDATE_OBJECTS` turns the test into a writer that always passes — nit

`object_matrix/mod.rs:816-819`. This is intended (regenerate, then review the diff), and the
variable is not set by any check. If it leaked into a CI environment, the comparison would be off
silently. Print "rewrote <file>, not compared" so a log shows it. [read]

### F3. Workdirs are never removed — nit

`common/mod.rs:346-353` (`test_dir`, `Workdir::new`) clears a directory only when it is reused,
and nothing removes it after the test. That is about 1,500 row directories per token per run under
`CARGO_TARGET_TMPDIR`.
Fine in the Nix sandbox. In a developer's `target/` it adds up across runs. [read]

### F4. `names.dedup()` is a no-op — nit

`object_matrix/mod.rs:470`. `dedup` removes only consecutive duplicates, and no `Kind::usage` of a
secret kind (`:61-68`) contains `CKA_UNWRAP` or `CKA_DERIVE`, so nothing is ever removed. If a kind
gained one, the duplicate would not be adjacent and a template with the attribute twice would
follow. Use `sort` + `dedup`, or a `BTreeSet`. [read]

## Design

- Pinning whole outcome tables, generated by the test and reviewed as a diff, is the right shape
  for "what cakeys makes of objects it did not create". It covers non-extractable, sensitive and
  always-authenticate legacy keys that the reference suite's clean fixtures never make.

## Checked, no issue

- A missing committed file fails (`unwrap_or_default` gives an empty string, which never equals
  the table).
- Batching (`batch`) bounds sessions for tpm2-pkcs11. Software tokens run unbounded in one
  session.
- Rows the token refuses to hold are recorded as such ("not created"), not dropped, so a module
  that starts accepting them changes the table.
